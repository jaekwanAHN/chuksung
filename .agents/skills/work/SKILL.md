# 이슈에서 PR까지

작업 순서는 **이슈 생성·선택 → 기획 → 사용자 검수 → 구현 → 필요한 검증 → PR**이다.
정상 흐름의 승인 지점은 기획 검수 한 곳이다. 승인받은 범위 안에서는 커밋·푸시·PR 생성
직전에 다시 진행 여부를 묻지 않는다. PR 생성이 종료점이며 머지·배포는 포함하지 않는다.
이 스킬은 Codex 대화에서 실행하는 절차이고, 별도 예약 실행이나 백그라운드 서비스가 아니다.

## 입력과 작업 환경

- `$work 164` 또는 이슈 URL: 해당 이슈를 대상으로 읽는다.
- `$work 체크박스 연타 후 상태가 되돌아가는 문제`: 중복 이슈를 찾고 없으면 새 이슈 초안을 만든다.
- `$work`: 열린 이슈의 우선순위와 의존 관계를 보고 착수 가능한 한 건을 권고 선정한다.
  `priority:` 라벨이 있으면 high → medium → low 순서를 따른다.
- 정보가 충분하면 대상 확인만을 위한 승인 단계를 추가하지 않고 기획까지 진행한다.
  후보가 서로 다른 제품 결정을 요구하는 등 추론할 수 없는 정보만 짧게 질문한다.

현재 저장소와 적용되는 `AGENTS.md`, 이슈·PR 템플릿, 패키지 명령을 확인한다.
프로젝트의 하드 룰·컨벤션·워크트리 도구·검증 기준을 원본에서 읽고 이 스킬에 복사하지 않는다.
사용자의 이번 작업 지시와 기존 승인 범위가 우선이다. 예전 명령에 있는 별도 푸시 승인이나
머지 단계는 이 흐름에 자동으로 가져오지 않는다. 샌드박스·조직 정책의 도구 권한은 별개다.

이 저장소의 `AGENTS.md` 「Git 워크플로」에 따라 기본 체크아웃에서
`pnpm wt:new <브랜치>`로 최신 기본 브랜치의 작업 환경을 준비한다.
슬롯이 부족하면 `AGENTS.md` 「Git 워크플로」의 병합 확인 기준에 따라 main에 병합된
워크트리를 기본 체크아웃에서 `pnpm wt:rm <브랜치> --delete-branch`로 정리하고
`pnpm wt:new <브랜치>`를 재시도한다. 삭제 대상 선택이나 소유 세션 종료 여부를 다시
묻지 않는다. 미병합 작업·병합 후 추가 커밋·커밋되지 않은 변경은 보존하고 `--force`는
사용하지 않는다. 정리 가능한 대상이 없을 때만 슬롯 부족을 보고한다.
정해진 이슈의 기존 PR·브랜치가 있으면 소유권과 현재 상태를 확인하고 중복 작업을 피한다.

## 1. 이슈 생성·선택

GitHub CLI가 있으면 필드를 좁혀 읽는다. 동등한 GitHub 도구가 있으면 사용해도 된다.

```bash
gh issue list --state open --limit 100 --json number,title,labels,url
gh issue view <번호> --json number,title,state,labels,body,url
```

문제 설명으로 시작하면 열린 이슈와 관련된 닫힌 이슈를 검색한다. 기존 이슈와 맞으면 재사용하고,
닫힌 이슈는 재발·다른 조건인지 확인한다. 대상 저장소가 다른 URL을 현재 저장소의 이슈로 취급하지 않는다.

새 이슈는 최신 저장소 양식에 맞춰 문제·영향·확인한 증거·기대 결과를 적는다.
코드 위치에는 확인 커밋을 붙이고 관측, 가설, 미승인 구현 후보를 구분한다.
원인을 모른다는 이유로 등록을 막거나 이슈 본문에 상세 구현 계획을 강제하지 않는다.

아직 승인되지 않은 새 이슈는 초안으로 유지하고 기획 검수 때 본문·라벨을 함께 제시한다.
이미 생성까지 명시적으로 승인된 경우는 그 범위에서 생성한다. 새 이슈 생성은 아래처럼
본문 파일을 사용하고, 번호를 받아 이후 PR과 연결한다.

```bash
gh issue create --title <제목> --body-file <본문파일> --label <라벨>
```

## 2. 기획과 검수

이슈의 완료 조건과 기존 요구사항을 현재 코드에 대조한다. 원인·영향을 판단하는 데 충분한
가장 작은 증거를 모은다. 행동 결함은 해당 동작을 재현하고, 구조·문서 문제는 코드·참조를
확인한다. 수정 전 수치는 숫자 델타가 완료 조건일 때만 측정한다.

다음을 한 번에 제시한다.

1. **대상·완료 조건:** 기존 이슈 링크 또는 새 이슈 본문·라벨 초안.
2. **현재 증거:** 확인된 원인, 미확인 전제, 사용자에게 생기는 영향.
3. **구현 계획:** 권고 방향, 의미 있는 대안, 영향 파일·화면·API·DB와 작업 범위.
4. **검증 계획:** 어떤 완료 조건을 어떤 검사로 확인할지, 테스트를 생략하면 그 이유.
5. **승인 범위:** 필요한 이슈 생성, 구현, 선택한 검증, 커밋, 작업 브랜치 푸시, PR 생성까지.

마지막에 이 계획으로 PR 생성까지 진행해도 되는지 묻고 **명시적인 응답을 기다린다**.
질문 도구가 승인 응답을 지원하지 않으면 일반 대화로 묻는다. 침묵이나 시간 경과를 승인으로
해석하지 않는다. 구현 파일을 수정하기 전에 검수를 마친다. 수정 요청이면 계획을 고쳐 검수받는다.

검증은 이슈 라벨 하나로 고르지 않고 완료 조건과 변경 경로로 정한다.

| 작업 성격 | 선택 기준 |
|---|---|
| 문서·스킬·정적 설정 설명 | diff와 참조·구조 확인으로 충분하면 런타임 테스트 생략 |
| 계산·상태·스크립트 로직 | 위험을 직접 확인하는 관련 unit 또는 작은 실행 시나리오 |
| UI·API 동작 결함 | 같은 재현과 영향 경로의 통합/E2E 검증 |
| 인증·공통 탐색·테스트 인프라 | 전역 영향에 맞는 넓은 회귀 검증 |
| 성능 등 정량 목표 | 수정 전후 동일 조건·명령의 측정 |

저장소의 필수 lint/build·스키마 검사 등은 별도로 적용한다. '테스트 선택'은 필수 검사를
무시하거나 실패한 테스트를 생략한다는 뜻이 아니다. 테스트를 불필요하게 새로 만들거나
모든 작업에 전체 테스트·성능 측정을 일괄 실행하지 않는다.

## 3. 승인 후 구현·검증

승인 내용과 범위, 이슈 번호, 브랜치·워크트리, 선택한 검증을 작업 기록에 남긴다.
기록 위치는 저장소 관례를 따르고, 없으면 세션 요약으로 유지한다. 재개할 때는 이 기록과
실제 Git·GitHub 상태를 대조해 완료한 단계를 반복하거나 승인을 다시 요구하지 않는다.

필요한 새 이슈를 생성한 뒤 승인된 계획을 구현한다. 관련 프로젝트 문서와 프레임워크
버전 지침을 읽고, 변경 diff를 직접 검토한다. Git 작업에서는 `git diff --check`를 실행하고
선택한 검사만 수행한다. 실패하면 승인 범위 내 원인을 수정하고 영향 검사만 다시 실행한다.
검증 결과의 저장 위치는 저장소 규칙을 따른다.

진행 중에는 주요 발견과 결과를 짧게 보고하되 매 단계에서 대화를 끝내지 않는다.
일상적인 구현 선택·동일 범위의 실패 수정은 계속 진행한다. 다음 경우에는 필요한 부분만
멈추고 근거와 해결에 필요한 선택을 알린다.

- 완료 조건·제품 동작·영향 범위를 실질적으로 바꾸어야 하는 경우: 바뀐 계획의 검수.
- 재현되지 않아 이슈의 전제가 성립하지 않는 경우: 확인 결과와 대상 재판단.
- 필수 권한·환경·사용자 결정이 없어 진전할 수 없는 경우: 구체적인 차단 원인.
- 필수 검사 실패를 승인 범위에서 해결할 수 없는 경우: 실패 증거. 통과했다고 보고하지 않는다.

시간 제한이나 네트워크 오류로 원격 쓰기의 성공 여부가 불명확하면 이슈·브랜치·PR의 실제
상태를 먼저 조회한다. 같은 생성 명령을 바로 반복해서 중복 이슈·PR을 만들지 않는다.

## 4. 커밋·푸시·PR

선택한 검증을 완료하고 diff가 승인 범위와 맞는지 확인한다. 이번 작업의 파일만 명시적으로
스테이징해 저장소 형식으로 커밋하고 작업 브랜치를 푸시한다. 기본 브랜치에는 직접 푸시하지 않는다.

기본 브랜치와 저장소의 PR 템플릿을 확인한다. 본문에는 결과·변경 요지와 `Fixes #<번호>`를
담되, 이슈 일부만 해결했다면 자동 종료 문구 대신 참조를 사용하고 남은 범위를 설명한다.
검증 결과의 위치·본문 형식은 저장소 규칙을 따른다. 정확한 본문을 임시 파일에 써서 넘긴다.

```bash
git push -u origin <작업브랜치>
gh pr list --head <작업브랜치> --state all --json number,state,url
gh pr create --base <기본브랜치> --head <작업브랜치> --title <제목> --body-file <본문파일>
```

기존 열린 PR이 있으면 재사용한다. 이미 머지된 브랜치에는 추가 커밋을 푸시하지 않는다.
PR 생성 후 다시 조회해 URL·대상/작업 브랜치·이슈 연결을 확인하고 완료를 보고한다.
기본 종료점은 PR 생성이므로 CI 완료를 기다리거나 자동 머지·이슈 수동 종료를 하지 않는다.
CI 상태를 언급하면 실제 조회 결과와 아직 진행 중인 상태를 구분한다.

최종 응답에는 **PR 링크, 변경 요약, 수행한 검증과 테스트 생략 이유(해당 시), 남은 제한**을
간결하게 적는다. PR 검토를 위해 작업 브랜치·워크트리를 남기며, 머지 뒤 정리는 저장소
규칙에 따라 이 작업의 소유 세션이 수행한다.
