`AGENTS.md` 「작업 절차」 8단계의 **단일 진입점**이다.
이 커맨드 하나로 이슈 선정 → 재현 → 구현 → 검증 → PR → 머지 → 정리까지 끝낸다.

인자: $ARGUMENTS

## 동작 원칙

**체크포인트에서만 멈춘다.** 그 사이 구간은 진행해도 되는지 묻지 않고 이어서 실행한다.
반대로 체크포인트는 **건너뛰지 않는다** — 사람이 판단해야 하는 지점이라서 둔 것이지
확인 절차가 아니다.

체크포인트는 `AskUserQuestion` 으로 같은 세션 안에서 처리한다. 사용자가 커맨드를
다시 칠 필요는 없다.

| 지점 | 무엇을 묻나 |
|---|---|
| **CP0** 프리플라이트 | (질문 아님 — 더티 트리일 때만 멈춤) |
| **CP1** 대상 확정 | 어떤 이슈를 할지 / 새로 만들지 |
| **CP2** 계획 승인 | 원인·수정 방향·영향 범위·검증 계획 — **여기 승인 전엔 코드를 고치지 않는다** |
| **CP3** 푸시 직전 | diff·PR 본문 검토 — **되돌릴 수 있는 마지막 지점** |
| **CP4** CI 결과 후 | 머지할지 / 실패를 고칠지 |

이 밖에도 **재현이 안 되거나, 원인이 갈리거나, 어느 단계든 실패하면 그 자리에서
멈추고 보고한다.** 임의로 판단해 넘어가지 않는다.

## CP0. 프리플라이트 — 지난 작업 정리 + 시작 상태 확보

물어보지 않고 실행한다. 단, 3번에서 더티 트리를 발견하면 멈춘다.

1. **머지된 로컬 브랜치 정리.** 로컬 브랜치마다 PR 상태를 확인해 머지된 것을 지운다.

   ```bash
   git branch --format='%(refname:short)' | grep -v '^main$'
   # 각 브랜치에 대해:
   gh pr list --head <브랜치> --state merged --json number,title
   ```

   `git branch --merged` 만으로 판정하지 말 것 — 스쿼시 머지된 브랜치는 잡히지 않는다.
   머지 확인된 브랜치는 `git branch -D <브랜치>` 로 삭제한다.

   **원격 브랜치는 지우지 않는다.** 머지 후에 문제를 발견할 수 있어 의도적으로 남긴다
   (저장소도 `delete_branch_on_merge: false` 로 맞춰져 있다).

   **지우지 않은 브랜치는 한 줄로 보고한다.** 조용히 넘어가면 열린 채 잊힌 PR이
   계속 쌓인다. 예: `남은 브랜치: chore/foo (PR #58 OPEN), bar (PR 없음)`

2. **worktree 정리.** `git worktree list` 에 머지된 브랜치의 worktree가 있으면
   `git worktree remove <경로>` 로 제거한다. 이 저장소는 worktree를 기본으로 쓰지 않는다
   — `.env.local`·`node_modules`·`.claude/settings.local.json` 이 gitignore 대상이라
   새 worktree는 부트스트랩 없이는 빌드·E2E가 실패한다.

3. **더티 트리 확인.** `git status --porcelain` 에 변경이 있으면 **여기서 멈추고**
   커밋할지, 스태시할지, 버릴지 묻는다.

4. **main 최신화.** `git checkout main && git pull origin main`

## CP1. 대상 확정 — 이슈가 없으면 만들고, 있으면 그것을 푼다

인자의 형태로 갈린다.

**(a) 숫자 (`/work 75`)** — 이슈를 읽고 그대로 진행한다. 이 경로에는 확인 질문이 없다.

```bash
gh issue view 75 --json number,title,state,labels,body \
  --jq '"[\(.state)] #\(.number) \(.title)\n라벨: \(.labels|map(.name)|join(", "))\n\n\(.body)"'
```

**`--json` 없이 `gh issue view` 를 쓰지 말 것.** 이 환경의 gh(2.46.0)는 폐기된
Projects classic 필드를 함께 요청해 GraphQL 에러로 실패한다. `--json` 을 붙이거나
`gh api repos/:owner/:repo/issues/<번호>` 를 쓰면 정상 동작한다.

**(b) 문제 설명 (`/work "헤더 날짜가 안 맞음"`)** — **자동으로 중복을 판정하지 않는다.**

```bash
gh issue list --state open --limit 50
gh issue list --state open --search "<핵심 키워드>"
```

로 열린 이슈를 훑고, 관련 있어 보이는 후보를 근거와 함께 제시한 뒤 고르게 한다.

```
"헤더 날짜가 안 맞음" 과 관련 있어 보이는 이슈:

  #71  헤더의 '오늘' 라벨이 일간 플래너와 다른 날짜를 표시   bug, priority: medium
  #79  헤더 테마 라벨 하이드레이션 불일치 + 첫 페인트 테마 FOUC   bug, priority: medium
```

선택지: `#71 진행` / `#79 진행` / `새 이슈로 진행` / `취소`

**(c) 인자 없음 (`/work`)** — 우선순위 라벨로 목록을 뽑아 고르게 한다.
번호 순서가 아니라 라벨이 기준이다.

```bash
gh issue list --label "priority: high" --state open
# 비어 있으면 medium → low 순으로 내려간다
```

**새 이슈를 만들기로 했다면 여기서 만들지 않는다.** 이슈 본문의 「현상 / 재현 /
원인·메커니즘」은 관측된 것만 적어야 하므로(`.github/ISSUE_TEMPLATE/`), 3번 재현을
마친 뒤 CP2에서 본문 초안과 함께 승인받아 생성한다.

## 2~3. 재현·계측

**이슈에 적힌 파일·줄 번호는 밀려 있다고 가정한다.** 이슈는 확인한 커밋 기준으로
작성되므로, 현재 코드에서 해당 지점을 다시 찾는다.

- 이슈의 관측이 **지금도 재현되는지** 먼저 확인한다. 재현되지 않으면 멈추고 보고한다
  — 이미 고쳐졌거나 조건이 다른 것이므로 이슈를 닫는 게 맞을 수 있다
- 브라우저로 눈으로 봐야 하는 이슈(하이드레이션·FOUC·레이아웃)는 **직접 확인할 수 없다.**
  재현 조건을 정리해 사용자에게 확인을 요청하고 멈춘다
- `performance` 라벨이면 **수정 전 기준선을 측정한다**: `pnpm perf --page <경로>`
  (`docs/perf/README.md` 참조). 이 라벨은 `docs/perf` 원장과 한 쌍이다
- **원인이 여럿으로 갈리면 분리한다.** 하나의 PR에 묶지 말고 어느 것을 할지 묻는다

## CP2. 계획 보고 → 승인

아래 네 가지를 보고한다. **승인 전에 코드를 수정하지 않는다** — 브랜치 생성도 승인 후다.

1. **원인 요약** — 메커니즘까지. "왜 그렇게 보이는가"가 아니라 "무엇이 그렇게 만드는가"
2. **수정 방향** — 대안이 있으면 **권고안을 명시**하고 트레이드오프를 밝힌다.
   길이는 맞추지 않는다 — 한 줄로 충분하면 한 줄로, 부족하면 필요한 만큼 쓴다
3. **영향 범위** — 건드릴 파일 목록, 다른 화면에 번지는 부분, 스키마 변경 여부
4. **검증 계획** — `pnpm lint && pnpm build` 외에 E2E가 필요한지, perf 전후 측정이
   필요한지, 사람이 눈으로 봐야 하는 부분이 있는지

**CP1에서 새 이슈로 정했다면 이슈 본문 초안도 함께 제시한다.** 승인 시 먼저 이슈를
만들고 번호를 확보한다.

```bash
gh issue create --title "<제목>" --body-file <초안> \
  --label "<bug|tech-debt|...>" --label "priority: <high|medium|low>"
```

승인 후 브랜치를 만든다. 이름은 `<type>/<kebab-case-요약>`.

```bash
git checkout -b fix/header-today-label
```

## 4~5. 구현

**구현을 시작하기 전에 `AGENTS.md` 「하드 룰」 절을 다시 읽는다.** 그 절의 항목 대부분은
`tsc`·lint·build 가 잡지 못해 코드 리뷰까지 가서야 드러나고, 그때는 6번 검증을 통과한
뒤라 여기로 되돌아오는 비용이 가장 크다. 「컨벤션」도 함께 지킨다.

**여기에 룰을 복사해 두지 않는다.** 단일 원본은 `AGENTS.md` 다 — 사본을 두면 원본이
바뀔 때 한쪽만 고쳐지고, 그 어긋남은 아무 신호 없이 남는다. 실제로 이 자리에 있던
사본은 10개 중 8개만 담고 있었다.

**설계 배경·근거·한계는 코드 주석이 아니라 `docs/` 문서에 남기고 코드에는 포인터만 둔다.**
새 문서를 만들었으면 CP3의 변경 목록에 포함한다.

## 6. 검증

```bash
npx tsc --noEmit && pnpm lint && pnpm build
```

`tsc --noEmit` 을 먼저 돌린다. `pnpm build` 도 타입을 보지만 훨씬 느리고, 타입
오류를 먼저 걷어내면 build 를 한 번만 돌려도 된다.

- E2E가 필요하면 `pnpm test:e2e <spec>` 으로 좁혀 돌리고, 마지막에 전체를 한 번
- `performance` 라벨이면 수정 후 측정 + **`docs/perf/` 에 전후 델타 기록**
- 실패하면 고친다. **고쳐지지 않으면 멈추고 보고한다** — 실패를 안고 CP3로 넘어가지 않는다

**회귀 테스트를 추가했다면 그 테스트가 수정 없이는 실패하는지 확인한다.** 수정을
잠시 되돌려 새 테스트가 빨간불인 것을 보고 복구한다. 이 확인을 건너뛰면 아무것도
잡지 못하는 테스트가 통과하는 것만 보고 넘어가게 된다 — 회귀 방지라는 목적 자체가
사라진다. 확인했으면 CP3의 검증 결과에 그 사실을 적는다.

로컬 검증을 건너뛰지 말 것. main의 required check가 `lint-and-build` 와 `e2e` 두 개라
어차피 CI에서 걸리고, 그때는 왕복이 훨씬 비싸다.

## CP3. 푸시 직전 검토 — 되돌릴 수 있는 마지막 지점

먼저 커밋한다. 메시지는 `feat|fix|test|docs|refactor: 한국어 요약` 형식으로 **단순하게**
— 무엇을 바꿨는지, 필요하면 왜 그렇게 했는지까지다. 변경 목록을 늘어놓지 않는다.
그 상세는 바로 아래 PR 본문에서 쓴다 (`AGENTS.md` 「컨벤션」).

그리고 **푸시하기 전에** 아래를 제시하고 승인을 받는다.

- `git diff main...HEAD --stat` 과 변경의 요지
- **PR 본문 초안 전문** — `.github/pull_request_template.md` 의 3절
  (작업 내용 / 변경사항 / 관련 이슈)을 그대로 채우고, 관련 이슈에 `Fixes #<번호>`
- 검증 결과 (tsc/lint/build/E2E/perf 델타, 회귀 테스트 유효성 확인 여부)

검증 절차 자체는 PR 본문이 아니라 저장소 문서에 남긴다.

**푸시하면 원격에 공개된다.** 승인을 받은 뒤에만 아래를 한 덩어리로 실행한다.

```bash
git push -u origin <브랜치>
gh pr create --title "<제목>" --body-file <본문>
```

## CP4. CI 결과 확인 → 머지

PR 생성 직후 체크를 지켜본다. e2e는 수 분 걸린다.

```bash
gh pr checks --watch
```

**통과했으면** 결과를 보고하고 머지 여부를 묻는다. 승인 시:

```bash
gh pr merge --merge
```

기존 히스토리가 머지 커밋 방식이므로 `--merge` 를 쓴다.
main protection이 `strict: true` 라 **브랜치가 main보다 뒤처져 있으면 머지가 거부된다.**
그때는 `gh pr update-branch` 로 최신화하고 CI를 다시 기다린다.

**실패했으면** 실패한 잡의 로그를 확인해 원인을 정리한 뒤, 고칠지 물어본다.

```bash
gh run view <run-id> --log-failed
```

고치기로 하면 5~6번으로 돌아가고, 수정 커밋은 **CP3를 다시 거쳐** 푸시한다.

## 7~8. 머지 후 정리

머지가 확인된 뒤에만 실행한다.

```bash
git checkout main && git pull origin main
git branch -D <작업 브랜치>
```

- **원격 브랜치는 남긴다** (CP0과 같은 이유)
- 이슈는 `Fixes #<번호>` 로 **main 머지 시점에 자동으로 닫힌다.** 따로 닫지 않는다
- **머지된 PR 브랜치에 추가 커밋을 푸시하지 말 것** — 반영되지 않는다.
  후속 작업이 있으면 새 브랜치로, 즉 `/work` 를 새로 시작한다

마지막으로 한 줄 요약을 남긴다.

```
✅ #71 머지 완료 (PR #82) — 로컬 브랜치 정리, 원격 유지
   남은 priority: high — #75
```

## 이 커맨드를 고쳐야 할 때

돌리다 막히는 지점을 발견하면 — 빠뜨린 단계가 있거나, 매번 같은 걸 손으로 보완하고
있다면 — 그 자리에서 이 파일을 고친다. 다음 실행부터 반영된다.

단, **절차의 단일 원본은 `AGENTS.md` 「작업 절차」다.** 규칙 자체를 바꿀 때는
`AGENTS.md` 를 고치고 이 파일은 실행 방법만 따라가게 한다. 양쪽에 같은 규칙을
복사하면 한쪽만 고쳐진다.
