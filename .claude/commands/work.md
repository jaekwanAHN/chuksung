`AGENTS.md` 「작업 절차」의 단일 실행 진입점이다. 규칙의 원본은 `AGENTS.md`이고,
이 파일은 이슈 선정 → 증거 선택 → 구현 → 검증 → PR → 머지 → 정리 순서만 실행한다.

인자: $ARGUMENTS

## 운영 원칙과 체크포인트

체크포인트 사이에서는 승인 질문을 반복하지 않는다. 아래 네 지점은 건너뛰지 않는다.

| 지점 | 판단 |
|---|---|
| **CP1 대상 확정** | 어떤 이슈를 해결할지, 없으면 새 이슈로 만들지 |
| **CP2 계획 승인** | 원인·수정 방향·영향 범위·선택한 증거와 검증 |
| **CP3 푸시 승인** | 로컬 커밋 diff·PR 본문·검증 결과 |
| **CP4 머지 승인** | required CI 결과를 보고 머지할지 |

프리플라이트, 선택한 증거, 구현, 검증 중 실패하면 해당 지점에서 멈춰 근거와 다음
선택지를 보고한다. 임의로 실패를 무시하거나 관계없는 검증으로 대체하지 않는다.

## 0. 프리플라이트

기본 체크아웃에서 실행한다.

```bash
pnpm wt:preflight
```

0이 아니면 출력된 원인(기본 체크아웃 아님, 더티 트리, 빈 슬롯 없음)을 보고하고 멈춘다.
남은 워크트리는 지우지 않는다. 머지된 워크트리가 있으면 주인 세션이 끝났는지 사용자에게
묻고, 승인된 것만 출력된 `pnpm wt:rm ... --delete-branch`로 정리한다. 열려 있거나 PR이
없는 브랜치·워크트리는 한 줄로 보고하되 빈 슬롯이 있으면 계속 진행한다.

배경과 안전장치는 `docs/parallel-work.md`에 있으며 스크립트 동작을 여기서 다시 설명하지
않는다.

## 1. CP1 — 대상 확정

### 숫자 인자

질문 없이 해당 이슈를 읽는다. 이 환경의 `gh issue view`는 필드를 좁히지 않으면 폐기된
Projects classic 필드 오류가 날 수 있으므로 항상 `--json`을 쓴다.

```bash
gh issue view <번호> --json number,title,state,labels,body \
  --jq '"[\(.state)] #\(.number) \(.title)\n라벨: \(.labels|map(.name)|join(", "))\n\n\(.body)"'
```

### 문제 설명 인자

```bash
gh issue list --state open --limit 50
gh issue list --state open --search "<핵심 키워드>"
```

관련 후보와 근거를 제시하고 `기존 이슈 진행 / 새 이슈 / 취소` 중 고르게 한다. 자동으로
중복 여부를 단정하지 않는다.

### 인자 없음

`priority: high → medium → low` 순서로 열린 목록을 조회하고 사용자가 고르게 한다.

```bash
gh issue list --label "priority: high" --state open
```

새 이슈는 아직 만들지 않는다. 현재 증거가 있어야 템플릿을 추측 없이 채울 수 있으므로
3번 뒤 CP2에서 본문 초안을 함께 승인받는다.

## 2. 대상 확정 직후 워크트리 생성

CP1이 끝나면 코드 조사·계측도 실제 작업 환경에서 하도록 즉시 자리를 만든다. CP1은
워크트리 생성을 허용할 뿐 코드 수정 승인은 아니다.

```bash
pnpm wt:new <type>/<kebab-case-요약>
cd <출력된 워크트리 경로>
```

이후 머지 전까지 모든 조사·수정·검증·커밋은 이 워크트리에서 한다.

## 3. 전제 확인·증거 선택

라벨이 아니라 이슈의 **성공 기준**으로 필요한 프로필만 고른다.

| 프로필 | 언제 | 착수 전 증거 |
|---|---|---|
| **행동** | 사용자·API의 잘못된 동작 | 가장 작은 실패 시나리오 재현 |
| **구조** | 코드·설정·문서·동시성 불변식 | 현재 소스·설정·이력의 직접 증거 |
| **정량** | 성공 기준이 점수·시간·크기 델타 | 같은 하네스·조건의 수정 전 기준선 |
| **외부 관측** | CI·배포·원격 API·정책 | 해당 상태 API·로그 |

- 실행 재현은 **행동** 프로필에만 한다.
- 수정 전 수치는 `performance` 라벨 때문이 아니라 **정량 델타가 성공 판정에 필요할 때만**
  잰다. Lighthouse면 `docs/perf/measurement-contract.md`를 따른다.
- 객관적 브라우저 관측은 Playwright나 저장소의 `verify` 레시피로 확인한다. 주관적 판단
  또는 필요한 환경이 없을 때만 사용자에게 확인을 요청한다.
- 이슈의 파일·줄은 현재 체크아웃에서 다시 찾는다. 관측이나 전제가 무효면 멈춰 보고한다.
- 독립 원인이 여럿이면 한 PR에 모으지 말고 분리해 어느 쪽을 할지 묻는다.

판정 근거와 예외는 `docs/work-evidence-routing.md`를 참조한다. 선택하지 않은 프로필의
명령은 실행하지 않는다.

## 4. CP2 — 계획 승인

코드를 고치기 전에 다음을 보고하고 승인받는다.

1. **현재 증거와 원인** — 선택한 프로필, 확인 결과, 원인 메커니즘
2. **수정 방향** — 권고안과 필요한 대안·트레이드오프
3. **영향 범위** — 파일·화면·API·DB 범위
4. **검증 계획** — 성공 기준에 직접 대응하는 명령과 생략한 큰 게이트의 이유

새 이슈라면 확인 커밋을 적은 `.github/ISSUE_TEMPLATE/` 본문 초안도 제시한다. 승인 후
이슈를 생성해 번호를 확보하고 나서만 구현한다. 기존 이슈도 **CP2 승인 전 코드 수정은
금지**다. 조사 명령과 정량 기준선 기록은 코드 수정이 아니다.

```bash
gh issue create --title "<제목>" --body-file <본문> --label "<종류>" --label "priority: <등급>"
```

## 5. 구현

구현 직전 `AGENTS.md` 「하드 룰」과 「컨벤션」을 다시 읽는다. Next.js 코드를 바꾸면
해당 `node_modules/next/dist/docs/` 문서를 먼저 확인한다. 하드 룰을 이 파일에 복사하지
않는다.

설계 배경·근거·한계는 `docs/`에 남기고 코드에는 필요한 포인터만 둔다.

## 6. 선택형 검증

모든 변경에서 먼저 실행한다.

```bash
git diff --check
```

그 다음 실제 변경에 해당하는 것만 고른다.

| 변경 | 검증 |
|---|---|
| 문서·명령 설명 | 참조 경로·중복 문구 `rg`, 필요한 `--help` |
| React/Next/TypeScript·빌드 설정 | `pnpm lint && pnpm build` |
| 스크립트 | `pnpm lint` + 관련 `node --test <파일>`; 워크트리 도구·공용 하네스는 `pnpm test:unit` |
| 특정 UI·API 동작 | `pnpm test:e2e <관련 spec>` 또는 동일 Playwright/HTTP 시나리오 |
| 인증·공통 내비·E2E 인프라 | 전체 `pnpm test:e2e` |
| DB | `pnpm db:check` + 영향 API/E2E |
| 정량 | 수정 전과 같은 명령·계정·데이터 조건의 수정 후 측정 |
| 외부 상태 | 착수 전과 같은 API·상태·로그 조회 |

`next build`가 타입 검사를 포함하므로 최종 게이트 직후 별도 `tsc --noEmit`을 중복하지
않는다. 전역 영향이 아니면 로컬 전체 E2E를 반복하지 않고 required CI의 전체 스위트에
맡긴다.

새 회귀 테스트는 가능하고 안전하면 수정 전 실패를 관련 테스트 하나로 확인한다. 되돌림
위험이 더 크면 기존 코드가 새 assertion을 위반한다는 직접 증거를 남긴다. React/Next/API
diff만 선택한 기계 검증 뒤 `frontend-code-reviewer`로 하드 룰을 검토한다.

선택한 검증이 실패하면 고치고 다시 실행한다. 해결하지 못하면 CP3로 가지 않고 보고한다.

## 7. CP3 — 커밋과 푸시 전 검토

커밋 메시지는 `AGENTS.md` 형식을 따른다. 로컬 커밋 뒤 아래만 간결하게 제시한다.

- `git diff main...HEAD --stat`과 변경 요지
- `.github/pull_request_template.md` 3절을 채운 PR 본문 전문 (`Fixes #<번호>` 포함)
- **선택한** 증거·검증 결과와 선택 이유

승인 뒤 한 덩어리로 푸시하고 PR을 만든다. 검증 절차 목록은 PR 본문에 반복하지 않는다.

```bash
git push -u origin <브랜치>
gh pr create --title "<제목>" --body-file <본문>
```

## 8. CI와 CP4 — 머지 승인

```bash
gh pr checks --watch
```

required checks가 모두 통과하면 결과를 보고하고 머지 승인을 받는다. 실패하면 실패 로그와
원인을 보고해 수정 승인을 받고 5~7번으로 돌아간다. main보다 뒤처져 보호 규칙이 막으면
브랜치를 최신화하고 CI를 다시 확인한다.

```bash
gh run view <run-id> --log-failed
gh pr update-branch
```

승인 시 기존 히스토리와 같은 merge commit 방식을 쓴다.

```bash
gh pr merge --merge
```

## 9. 머지 후 정리

이 작업을 수행한 세션이 기본 체크아웃으로 나가 자기 워크트리만 정리한다.

```bash
cd <기본 체크아웃>
pnpm wt:rm <브랜치> --delete-branch
```

원격 브랜치는 남긴다. 머지된 브랜치에는 추가 커밋을 푸시하지 않는다. 마지막으로 PR·이슈,
정리 결과, 슬롯 현황과 남은 최고 priority 이슈를 한 줄로 보고한다.

## 이 커맨드를 고칠 때

단계·필수 정책은 `AGENTS.md`, 판단 배경·전후 기록은 `docs/work-evidence-routing.md`, 실행
분기만 이 파일에 둔다. 스크립트가 집행하거나 출력하는 내부 동작을 다시 복사하지 않는다.
