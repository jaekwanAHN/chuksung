# `/work` 증거·검증 라우팅

이 문서는 #147에서 확인한 `/work` 변경 전 문제와 변경 후 판단 기준을 기록한다.
절차의 단일 원본은 `AGENTS.md`, 실제 실행 순서는 `.claude/commands/work.md`다. 이 문서는
매 작업마다 전부 읽는 프롬프트가 아니라, 라우팅의 근거·예외·한계를 확인할 때 쓰는
참조 문서다.

## 목표

이슈 해결에 필요한 것은 고정된 단계의 완주가 아니라 다음 두 질문에 답할 증거다.

1. **착수 전:** 이슈의 전제와 원인이 현재도 유효한가?
2. **수정 후:** 이슈에 적힌 성공 기준을 충족했는가?

각 질문에 답하는 가장 싼 충분한 증거를 고른다. 증거를 줄인다는 말은 검증을 생략한다는
뜻이 아니다. 실행 재현이 구조 결함을 입증하지 못하거나 앱 빌드가 문서 링크를 검증하지
못하는 것처럼, 관계없는 명령을 빼고 실패 신호가 있는 검증에 비용을 집중한다는 뜻이다.

## 변경 전

`db6323d` (2026-08-25) 기준.

| 항목 | 기존 동작 | 문제 |
|---|---|---|
| 착수 전 증거 | 모든 이슈에 현재 관측의 실행 재현 요구 | 구조·문서·외부 장애에도 런타임을 준비하고 같은 사실을 반복 확인 |
| 수정 전 측정 | `performance` 라벨이면 Lighthouse 기준선 | a11y·CI 시간처럼 다른 라벨의 정량 작업은 빠지고, 숫자가 성공 기준이 아닌 성능 분류에는 과잉 측정 |
| 워크트리 시점 | `AGENTS.md`는 대상 직후, `/work`는 CP2 승인 뒤 | 기본 체크아웃에서 재현한 상태와 실제 수정 환경이 달라질 수 있음 |
| UI 관측 | 브라우저 이슈는 직접 확인 불가로 중단 | Playwright와 `verify` 레시피로 객관적으로 확인 가능한 항목도 사람에게 넘김 |
| 최종 검증 | 새 워크트리마다 build → tsc → lint, 관련 E2E 뒤 전체 E2E | `next build` 직후 타입 검사를 중복하고 CI가 실행할 전체 스위트를 로컬에서 다시 반복 |
| 명령 문맥 | `/work`가 스크립트 내부 동작과 배경까지 설명 | `CLAUDE.md`가 불러오는 `AGENTS.md`와 합쳐 기본 입력이 27,276자까지 증가 |

재현 자체를 없애는 것도 답은 아니다. #109처럼 착수 전 관측이 잘못된 최초 가정을
기각한 사례가 있다. 문제는 **행동 결함에 유용한 증거를 모든 종류의 이슈에 적용한 것**이다.

### 기본 문맥 크기 변화

파일의 UTF-8 바이트 수를 토큰 비용의 안정적인 대리값으로 쟀다. `CLAUDE.md`는
`AGENTS.md`를 import하므로 `/work` 호출 때 기본으로 함께 읽히는 세 파일만 합산했다.

```bash
wc -c AGENTS.md .claude/commands/work.md CLAUDE.md
```

| 기본 입력 | 변경 전 | 변경 후 | 차이 |
|---|---:|---:|---:|
| `AGENTS.md` | 10,594 B | 11,522 B | +928 B |
| `.claude/commands/work.md` | 16,671 B | 9,290 B | **-7,381 B (-44.3%)** |
| `CLAUDE.md` | 11 B | 11 B | 0 |
| **합계** | **27,276 B** | **20,823 B** | **-6,453 B (-23.7%)** |

판단 배경을 담은 이 문서는 기본 입력에 넣지 않는다. 프로필 판정이 애매하거나 절차를
고칠 때만 열어 보므로, 실행 규칙을 줄인 만큼을 다른 상시 문맥으로 옮기지 않았다.

## 변경 후: 성공 기준으로 프로필을 고른다

라벨은 검색과 우선순위의 힌트일 뿐 증거 프로필을 결정하지 않는다. 이슈 본문의 현상과
성공 기준으로 아래 프로필을 하나 이상 고르고, CP2에서 선택 이유와 명령을 보고한다.

| 프로필 | 선택 조건 | 수정 전 증거 | 수정 후 증거 |
|---|---|---|---|
| **행동** | 사용자·API에서 잘못된 동작을 관측할 수 있음 | 가장 작은 실패 시나리오 1회 | 같은 시나리오 + 관련 회귀 테스트 |
| **구조** | 코드·설정·문서의 불변식, 의존 관계, 동시성이 문제 | 현재 소스·설정·이력·정적 검사 | 관련 unit·lint·검색·diff 등 불변식을 직접 보는 검사 |
| **정량** | 성공 기준이 점수·시간·크기·요청 수 같은 숫자 델타 | 같은 하네스의 기준선 | 같은 명령·계정·데이터 조건의 수정 후 값과 델타 |
| **외부 관측** | CI·배포·원격 API·정책처럼 로컬 밖 상태가 원인 | 해당 API·상태·로그 | 같은 조회를 반복해 상태 전이 확인 |

한 이슈가 행동+정량처럼 둘 이상일 수는 있다. 그렇다고 네 프로필을 모두 실행하지는
않는다. 원인이 서로 독립적이면 프로필을 늘리는 대신 이슈와 PR을 나눈다.

### 착수 전 판단 규칙

- **행동 프로필만 실행 재현한다.** 재현되지 않으면 이미 수정됐는지, 조건이 달라졌는지
  보고하고 계획 승인으로 넘어가지 않는다.
- **정량 프로필만 수정 전 수치를 잰다.** “성능 관련”이라는 분류만으로는 부족하고,
  성공 판정에 before/after 숫자가 실제로 필요해야 한다.
- 구조 프로필은 실행 결과가 아니라 문제의 불변식을 직접 확인한다. 경쟁 조건이면 잠금·
  트랜잭션 경로, 문서면 중복·모순·깨진 참조가 증거다.
- 외부 관측 프로필은 로컬 모사보다 실제 상태 API·로그가 싸고 정확하면 그것을 쓴다.
- 객관적 UI 상태·레이아웃·하이드레이션은 Playwright나 저장소의 `verify` 레시피로 확인한다.
  취향 판단처럼 주관적이거나 필요한 환경이 없을 때만 사용자에게 관측을 요청한다.
- 이슈의 파일·줄 번호는 확인한 커밋의 단서다. 현재 코드에서 다시 찾되, 전체 런타임
  재현으로 확대하지 않는다.

## 수정 후 검증 라우터

모든 작업은 `git diff --check`를 통과해야 한다. 그 다음에는 실제로 바뀐 경로와 성공
기준에 해당하는 행만 더한다.

| 변경 경로·위험 | 로컬 검증 |
|---|---|
| 문서·명령 설명만 | 참조 경로·명령·중복 문구를 `rg`로 확인하고 필요한 `--help` 실행 |
| React/Next/TypeScript 또는 빌드 설정 | `pnpm lint && pnpm build` |
| `scripts/**/*.mjs` | `pnpm lint` + 관련 `node --test <파일>`; 워크트리 도구·공용 하네스면 `pnpm test:unit` |
| 특정 UI·API 동작 | 관련 `pnpm test:e2e <spec>` 또는 Playwright/HTTP 시나리오 |
| 인증·공통 내비·E2E 인프라 등 전역 영향 | 로컬 전체 `pnpm test:e2e` |
| DB 스키마·마이그레이션 | `pnpm db:check` + 영향 API/E2E; 원격 `db:push`는 기본 체크아웃 직렬 규칙 유지 |
| 정량 성공 기준 | 수정 전과 정확히 같은 측정 명령·조건으로 수정 후 측정 |
| 외부 상태 | 착수 전에 쓴 것과 같은 API·상태·로그 조회 |

추가 규칙은 다음과 같다.

- 현재 Next.js의 `pnpm build`가 TypeScript 검사를 포함하므로 최종 게이트 직후
  `tsc --noEmit`을 다시 실행하지 않는다.
- 로컬 E2E는 영향 경로를 먼저 좁힌다. 모든 PR의 required `e2e` job이 전체 스위트를
  실행하므로, 전역 영향이 아닌 작업에서 로컬 전체 스위트를 관성적으로 반복하지 않는다.
- 새 회귀 테스트는 가능하고 안전한 범위에서 수정 전 실패를 확인한다. 상태를 되돌리는
  비용이나 위험이 더 크면 기존 코드가 새 assertion을 위반한다는 직접 증거를 대신 남긴다.
- React/Next/API diff만 선택한 기계 검증 뒤 `frontend-code-reviewer`의 하드 룰 검토를
  거친다. 문서·워크플로 diff에는 이 리뷰를 붙이지 않는다.
- 선택한 로컬 검증이 실패하면 원인을 해결하거나 멈춰 보고한다. required CI가 모두
  통과하기 전에는 머지하지 않는다.

## 단계와 체크포인트

변경 후 순서는 다음과 같다.

1. 프리플라이트
2. CP1 대상 확정
3. **대상 확정 직후 워크트리 생성**
4. 전제 확인·증거 선택
5. CP2 계획 승인 — 이 전에는 코드를 수정하지 않음
6. 구현과 선택형 검증
7. CP3 푸시 전 diff·PR 본문 검토
8. CI 후 CP4 머지 승인
9. 작업한 세션이 자기 워크트리 정리

CP2와 CP4는 그대로 유지한다. CP3도 원격 공개 전 사람 검토라는 운영 정책을 유지하되,
선택하지 않은 검증의 “미실행” 목록 대신 **선택한 증거와 결과만** 보고한다.

## 적용 예

- 클릭 시 저장되지 않는 버그: **행동**. 해당 동작을 재현하고 같은 E2E로 고친 뒤 확인한다.
- 잠금 없는 경쟁 조건: **구조**. 매번 운에 맡긴 런타임 재현 대신 임계 구역과 동시성 unit을 본다.
- Lighthouse 접근성 점수 개선: 라벨과 무관하게 **정량**. 같은 페이지를 전후 측정한다.
- CI 실행 시간 단축: **정량+외부 관측**. Actions 실행 분포를 전후 같은 기준으로 비교한다.
- `/work` 문구 정리: **구조**. 문서 모순·참조·명령 출력을 확인하며 앱 런타임은 재현하지 않는다.

## #147 검증 선택과 결과

이 변경은 **구조+정량** 프로필이다. 문서·명령·워크트리 안내만 바뀌며 UI·API 런타임은
바뀌지 않는다.

- 수정 전·후 같은 `wc -c` 명령으로 기본 입력 크기를 비교했다: **27,276 B → 20,823 B
  (-23.7%)**
- `git diff --check`, 참조 파일 존재 확인, 이전 고정 문구 `rg`: 통과
- `pnpm wt:new --help`: 통과
- `pnpm test:unit`: 5개 테스트 파일 통과
- `pnpm lint`: 통과
- `pnpm build`: 컴파일·Next TypeScript 검사·정적 페이지 생성 통과

lint/build는 문서 작업의 새 기본값이라서가 아니라, 전역 작업 절차를 바꾸는 #147의 완료
조건에 기존 CI 게이트 호환 확인이 명시되어 있어 한 번 실행했다. 런타임 경로와 렌더링
성능은 바뀌지 않으므로 로컬 E2E와 Lighthouse 전후 측정은 선택하지 않았다. 전체 E2E는
PR의 required CI에서 확인한다.

## 한계

- “가장 싼 충분한 증거” 선택에는 판단이 필요하다. 애매하면 더 넓은 명령을 자동 실행하기
  전에 CP2에서 대안과 비용을 제시한다.
- 브라우저·원격 계정·권한이 없으면 해당 증거를 만들 수 없다. 다른 프로필인 척 넘기지
  말고 환경 부재를 보고한다.
- 주관적 시각 품질과 제품 선택은 자동화할 수 없다. 객관적 DOM·픽셀·접근성 상태까지만
  도구로 확인하고 최종 취향 판단은 사용자에게 남긴다.
- 이 라우터는 CI required checks, 보안 하드 룰, CP2 승인, CP3 공개 전 검토, CP4 머지
  승인을 약화하지 않는다.

## 유지보수 경계

- 단계·필수 정책을 바꾸면 `AGENTS.md`를 먼저 고친다.
- `.claude/commands/work.md`에는 실행에 필요한 분기와 명령만 둔다.
- 왜 그 분기가 필요한지, 변경 전 사고와 보류한 대안은 이 문서에 남긴다.
- 스크립트가 이미 출력·집행하는 내부 동작은 `/work`에 다시 설명하지 않는다.
