# 인증 리다이렉트와 왕복 차단

로그인 상태에 따라 경로를 옮기는 곳이 셋 있다. 서로를 먹이면 무한 왕복이 되므로
**어느 리다이렉트가 무조건이고 어느 것이 조건부인지**와 그 근거를 남긴다.

관련 코드: `src/lib/auth-redirect.ts`, `src/lib/axios.ts`, `src/proxy.ts`,
`src/app/(auth)/login/page.tsx`

## 왕복이 만들어지던 경로

`apiClient` 인터셉터가 401 을 받으면 `/login` 으로 이동하고, `proxy` 는 인증 쿠키가
유효하면 `/login` 을 `/daily` 로 되돌린다. 둘 다 무조건이었기 때문에 **쿠키는 유효한데
API 만 401 을 내는 상황**에서 닫힌 순환이 만들어졌다.

```
/daily 마운트 → GET /api/tasks → 401 → /login → (쿠키 유효) → /daily → …
```

재현하면 8초 동안 45회 왕복한다(초당 약 5.6회 전체 페이지 로드). **브라우저가 끊어주지
않는다** — 매 사이클이 스크립트가 시작한 새 내비게이션이라 리다이렉트 상한
(`ERR_TOO_MANY_REDIRECTS`)에 걸리지 않는다. 서버가 307 을 연달아 냈다면 20홉쯤에서
브라우저가 멈췄겠지만 이 순환은 사용자가 탭을 닫기 전까지 계속되며, 그동안 매 사이클
API 를 호출한다.

쿠키와 API 응답이 엇갈리는 상황은 세션 만료가 아니다. 만료면 쿠키도 무효라 되돌림이
일어나지 않고 로그인 화면에서 멈춘다. 엇갈림은 RLS 거부, 서버 측 인증 상태 불일치,
`supabase.auth.getUser()` 의 일시적 실패(네트워크 순단·인증 서버 장애) 처럼 **세션이
살아 있는데도 개별 요청만 미인증으로 판정될 때** 드러난다.

## 마커로 끊는다

`apiClient` 가 `/login?session=invalid` 로 이동하고, `proxy` 는 그 마커가 있으면
`/daily` 로 되돌리지 않는다. 상태를 URL 에 실으므로 전체 페이지 이동을 거쳐도 서버까지
그대로 전달되고, 마커가 유실될 경로가 없어 차단이 결정적이다. 저장할 상태도 조정할
임계값도 없다. 파라미터 이름·값은 `src/lib/auth-redirect.ts` 한곳에 둔다 — 세 파일이
같은 규약을 공유하기 때문이다.

사용자는 사유를 안내받는 로그인 화면에서 멈춘다. 서버가 인증을 거부하는 중이므로
재로그인이 실제로 맞는 행동이다.

## 프록시는 낙관적으로만 판단한다

프록시는 `getUser()`(Auth 서버 왕복)가 아니라 `getClaims()`(JWKS 로 서명을 로컬
검증)로 세션을 본다. 이유는 성능이고 근거는 `docs/perf/deploy-latency.md` 에 있다 —
프록시는 프리페치를 포함한 모든 요청에서 실행되므로 왕복이 요청 수만큼 곱해진다.
Next 문서도 프록시에서는 쿠키만 읽고 DB·서버 조회를 피하라고 명시한다.

**그 결과 "쿠키는 통과하는데 API 는 401" 이 사고가 아니라 설계상 예정된 상태가 됐다.**

| | 프록시 (`getClaims`) | API (`withAuth` → `getUser`) |
|---|---|---|
| 검증 대상 | 서명과 `exp` 만, 로컬 | Auth 서버의 현재 판단 |
| 세션 무효화 반영 | 토큰 만료(1시간)까지 지연 | 즉시 |

서버가 세션을 무효화해도 프록시는 최대 1시간 통과시킨다. 그 사용자는 `/daily` 를 한 번
거친 뒤 API 401 → `/login?session=invalid` 로 도달한다. **대시보드가 잠깐 보였다가
튕기는 것은 결함이 아니라 이 구조의 결과다.**

되돌리지 않는 이유: 이걸 없애려면 프록시가 서버 검증을 해야 하는데, 그것이 정확히
제거 대상이던 비용이다. 정상 사용자의 모든 요청에 왕복을 부과하고 드문 무효화 케이스의
한 홉을 아끼는 거래는 성립하지 않는다. 인가는 `withAuth` 와 RLS 가 그대로 담당하므로
보안은 약해지지 않는다 — 프록시 통과는 화면 이동 허가일 뿐 데이터 접근 허가가 아니다.

**그래서 위의 마커 가드는 안전망이 아니라 상시 작동하는 필수 부품이다.** 낙관적 검증이
만드는 엇갈림을 매번 끊는 것이 그 역할이다.

## 일부러 하지 않은 것

**쿠키를 지우지 않는다.** 401 을 받은 시점에 `signOut()` 을 호출하면 되돌림의 근거인
쿠키가 사라져 순환이 구조적으로 소멸하지만, 그것은 **401 을 세션 무효로 단정**하는
것이다. 위에 적은 엇갈림 상황들은 세션이 멀쩡한데도 401 이 나오므로 오진 시 되돌릴 수
없는 강제 로그아웃이 되고, 인증 서버 일시 장애가 전 사용자 로그아웃 사고로 번진다.
게다가 `signOut()` 은 네트워크 왕복이라 실패할 수 있어 차단이 보장되지도 않는다.
세션 정리는 사용자가 로그인 버튼을 누르는 순간 어차피 이뤄진다.

**리다이렉트 횟수를 세지 않는다.** `sessionStorage` 에 반복 이동을 기록해 억제하는
방법은 임계값이 임의적이라 완화에 그치고, 이동을 취소한 뒤 사용자가 아무것도 불러오지
못한 화면에 이유 없이 남는다.

**인터셉터에 "이미 `/login` 이면 이동하지 않음" 가드를 두지 않는다.** 로그인 페이지는
`apiClient` 를 호출하지 않아 발동할 경로가 없다. 차단은 마커가 담당한다.

**원래 경로를 `next` 로 보존하지 않는다.** 재로그인 후 복귀 지점을 살리는 것은 별개
주제이므로 이 변경에 포함하지 않았다.

## 회귀 방지

`e2e/login.spec.ts` 의 "API 가 401 을 계속 반환해도 왕복하지 않는다" 가 `/api/tasks`
응답을 계속 401 로 채운 뒤 `/daily` 내비게이션이 최초 1회뿐인지 확인한다. `proxy` 의
마커 조건을 제거하면 이 테스트는 실패한다.

이 테스트 이전에는 **첫 응답만** 401 로 채웠다. 계속 채우면 왕복에 걸려 테스트가 끝나지
않았기 때문인데, 그 회피 자체가 결함의 증상이었다.

같은 파일에 낙관적 검증 전환에 딸린 회귀 방지선을 함께 둔다.

- **"`/` 로 진입해도 401 왕복 없이 /login 에서 멈춘다"** — `/` 는 보호 경로가 아니라
  프록시를 통과하므로 차단이 `/daily` 진입과 같은 방식으로 걸리는지 따로 확인한다.
- **"서명이 위조된 토큰은 보호 경로에서 차단된다"** — 로컬 검증으로 바꾼 이상, 검증을
  빠뜨린 구현(예: 서명 확인 없이 페이로드만 디코딩)이 그대로 통과시킬 수 있다.
  refresh 경로를 함께 막아 서명 검증만 격리해 확인한다.
- **"만료된 세션은 갱신되어 통과하고 새 쿠키가 내려온다"** — `updateSession` 의 쿠키
  갱신 책임이 빠지면 **토큰 수명마다 전원이 로그아웃된다.** 조용히 깨지는 종류라
  테스트 없이는 배포 후에야 드러난다.
