# API 남용 방어

`/api/*` 라우트 핸들러가 악의적인 요청과 다량 호출에 대해 어떤 가드를 두는지 정리한다.
구현은 `src/lib/api/route-helpers.ts`, `src/lib/api/rate-limit.ts` 에 모여 있다.

각 가드가 실제로 동작하는지 확인하는 재현 절차는 [`verification.md`](verification.md) 에 있다.
방어 코드를 고쳤다면 그쪽을 그대로 다시 돌린다.

## 이미 있던 방어선

새로 추가한 것과 겹치지 않도록, 기존에 성립하던 전제를 먼저 적는다.

| 위협 | 방어 |
| --- | --- |
| 타인 데이터 조회·수정 | 전 테이블 RLS + `auth.uid()` 정책. 목록 GET 이 `user_id` 필터 없이 나가도 DB 가 자른다 |
| 임의 컬럼 주입 | `parseBody` 의 zod 화이트리스트. 스키마에 없는 키는 제거된다 |
| ID 추측(IDOR) | `[id]` 라우트가 `.eq('id')` + `.eq('user_id')` 이중 조건 |
| SQL 인젝션 | PostgREST·RPC 모두 파라미터 바인딩. 문자열 연결로 SQL 을 만드는 곳이 없다 |
| RPC 무단 호출 | `completed_history`·`seed_daily_templates` 는 `security invoker` + `anon` 실행 권한 revoke |
| 내부 구조 노출 | `dbError` 가 Postgres 메시지를 감추고 코드만 매핑 |
| Open redirect | `/auth/callback` 이 `next` 를 내부 경로로만 허용 |
| 위험한 URL 스킴 | `job_postings.url` 은 zod 에서 `https?` 만 허용 |

## 1. 레이트 리밋

`withAuth` 가 인증 직후 사용자 단위로 호출량을 센다. 초과하면 `429` + `Retry-After`.

- 윈도: 60초 고정 윈도
- 상한: 읽기 300회 / 쓰기 100회 (`GET`·`HEAD` 를 읽기로 본다)
- 읽기와 쓰기는 버킷을 분리한다. 조회 폭주가 쓰기 예산을 잡아먹지 않게 하기 위함이다

**왜 user.id 로 세는가.** 인증 전 IP 기준으로 세려면 프록시 헤더를 신뢰해야 한다.
그리고 세션 쿠키가 없는 요청은 supabase-js 가 네트워크 호출 없이 로컬에서 끊으므로
(`_getUser` 가 access_token 부재 시 즉시 반환) 실제 비용이 드는 지점은 인증 통과 이후다.

**상한을 왜 이렇게 높게 잡았나.** 사람이 쓰다가 걸리면 안 되는 값이다. 연속 클릭,
페이지 전환 시 동시 조회, E2E 스위트 전체 실행이 모두 아래로 들어와야 한다.
목적은 정밀한 쿼터가 아니라 "무제한 → 유한"으로 만드는 것이다.

**한계 — 인스턴스당 상한이다.** 카운터가 인스턴스 메모리에 있다. 서버리스로 배포하면
인스턴스마다 버킷이 따로 잡히므로 전역 상한이 아니다. 전역 보장이 필요해지면 Redis 등
공유 저장소로 옮겨야 한다. 버킷 맵 자체가 메모리 압박 수단이 되지 않도록 항목 수가
`MAX_BUCKETS` 를 넘으면 만료분을 청소한다.

## 2. 본문 크기 상한

`parseBody` 가 64KB 를 넘는 본문을 `413` 으로 끊는다.

App Router 라우트 핸들러에는 Pages API 의 `bodyParser` 크기 제한이 적용되지 않는다.
`request.json()` 은 본문 전체를 메모리에 올린 뒤에야 값을 돌려주므로, zod 스키마의
`max()` 는 이미 다 읽고 난 다음에야 동작한다. 수백 MB 짜리 POST 하나로 프로세스
메모리를 밀어낼 수 있었다.

그래서 파싱 전에 두 번 막는다.

1. `Content-Length` 가 상한을 넘으면 바로 거절
2. 헤더가 없거나 거짓일 수 있으므로, 스트림을 읽으면서 누적 바이트를 세고 상한을
   넘는 순간 `reader.cancel()`

64KB 는 가장 큰 스키마 필드(`goals.content` 10,000자, `job_postings.notes` 5,000자)를
전부 한글 3바이트로 채우고 JSON 이스케이프까지 감안해도 여유가 있는 값이다.

## 3. 템플릿 시딩 시간 게이트

`GET /api/tasks` 는 일간 조회 시 활성 템플릿을 태스크로 시딩한다. 이 시딩 여부를
판정하는 시간 게이트가 쿼리 파라미터 `client_now` 하나에만 의존했다.

`client_now` 는 사용자의 로컬 벽시계다. 서버가 대신 계산할 수 없어서 클라이언트가
보낸다. 문제는 서버 시각과 대조하지 않아 아래가 통과했다는 것이다.

```
GET /api/tasks?scope=daily&target_date=2030-01-01&client_now=2030-01-01T23:59
```

게이트 세 조건을 모두 만족하므로 임의의 미래 날짜에 템플릿이 시딩된다. 날짜를 바꿔가며
반복하면 `활성 템플릿 수 × 요청 수` 만큼 행이 생긴다. RLS 안쪽이라 타인 데이터는 아니지만
저장소를 무제한으로 늘릴 수 있는 경로였다.

이제 `isTrustableClientNow` 로 두 가지를 확인한다.

- 형식이 `yyyy-MM-ddTHH:mm` 인가
- 서버 UTC 시각과의 차이가 24시간 이내인가

24시간인 이유: `client_now` 에는 오프셋 정보가 없어 실제 타임존만으로 최대 +14 / −12시간
(총 26시간 폭) 벌어질 수 있다. 여기에 기기 시계 오차를 얹으면 절댓값 24시간이 타임존
전체를 덮으면서도 "임의의 연도"는 막는 선이다. 게이트가 `client_now` 기준 ±1일 안으로
좁혀지므로 시딩 가능한 날짜가 실제 현재 시각 부근 며칠로 제한된다.

`target_date` 형식 검사도 함께 넣었다. 문자열 비교로 날짜를 비교하는 게이트라
`"9999"` 같은 값이 사전순 비교를 통과하는 경로를 없앤다.

## 4. 인증 왕복 축소

`src/proxy.ts` 의 matcher 에서 `api` 를 제외했다.

`supabase.auth.getUser()` 는 호출할 때마다 Supabase Auth 로 `GET /user` 네트워크 요청을
보낸다(`@supabase/auth-js` 의 `_getUser`). matcher 가 `/api/*` 까지 덮고 있어서 API 호출
하나마다 `updateSession` 에서 한 번, `withAuth` 에서 또 한 번, 총 2회 왕복이 발생했다.
레이트 리밋이 없던 상태와 겹치면 부하가 그대로 2배로 증폭된다.

세션 갱신이 깨지지 않는 이유: 라우트 핸들러의 `createClient()` 도 만료 토큰을 갱신하고,
쿠키 쓰기가 가능한 컨텍스트라 `setAll` 이 정상 동작한다. 프록시는 페이지 요청에서만
세션을 갱신하면 된다. `/auth/callback` 은 `/api` 밑이 아니라 그대로 프록시를 탄다.

## 5. `tz` 검증

`GET /api/tasks/history` 의 `tz` 가 검증 없이 RPC 로 전달됐다. 파라미터 바인딩이라
인젝션은 아니지만, 잘못된 타임존은 `at time zone` 에서 Postgres 예외를 일으키고
`DB_ERROR_MAP` 에 없는 코드라 `500` 으로 나갔다. `Intl.DateTimeFormat` 으로 실재하는
IANA 존인지 확인해 `400` 으로 돌려준다.

## 남은 것

- **전역 레이트 리밋**: 위에 적은 대로 현재는 인스턴스당이다. 다중 인스턴스 배포로
  가면 공유 저장소가 필요하다
- **계정당 총량 쿼터**: 분당 호출은 제한되지만 누적 행 수에는 상한이 없다. 100행/분을
  계속 유지하면 결국 늘어난다. 테이블별 상한이 필요하면 DB 제약으로 거는 편이 낫다
- **CSRF**: 상태 변경이 쿠키 인증에 의존한다. Supabase 세션 쿠키가 `SameSite=Lax` 라
  크로스사이트 POST 에 쿠키가 실리지 않고, `application/json` 본문은 프리플라이트를
  요구하므로 현재는 열려 있지 않다. 쿠키 옵션이나 CORS 설정을 바꾸면 재검토할 것
