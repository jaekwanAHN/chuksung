# 태스크 토글·삭제·편집의 경합 가드

`TaskCard` 한 장에는 같은 태스크를 건드리는 경로가 셋 있다 — 완료 토글, 삭제, 편집.
셋 다 서버 왕복을 하고 그중 토글만 낙관적 업데이트를 쓰기 때문에, 응답이 겹치면
캐시가 사용자의 마지막 의도와 어긋난다. 이 문서는 **무엇을 막고 무엇을 일부러
열어두는지**와 그 근거를 남긴다.

관련 코드: `src/app/(dashboard)/_hooks/tasks/useTaskMutations.ts`,
`src/app/(dashboard)/_components/tasks/TaskCard.tsx`

## 왜 막아야 하나 — 삭제된 항목이 되살아나는 경로

토글은 `onMutate` 에서 **리스트 전체 배열**의 스냅샷을 잡고, 실패하면 `onError` 가
그 배열을 통째로 되돌린다. 스냅샷은 토글이 시작된 시점의 목록이다.

```
1. 토글 시작 → 스냅샷 [A, B, C] 저장, 낙관적으로 A 를 완료로 표시
2. 응답 대기 중 B 삭제 성공 → 캐시 [A, C]
3. 토글 실패 → onError 가 스냅샷 복원 → 캐시 [A, B, C]
                                              ↑ 삭제된 B 가 되살아난다
```

되살아나는 것은 **실패 롤백** 경로다. 성공 경로(`onSuccess`)는 `map` 으로 해당
항목만 교체하므로 이미 사라진 항목에는 아무 영향이 없다.

반대 방향도 같다. 삭제 응답을 기다리는 동안 토글을 걸면 위와 같은 조합이 만들어진다.

편집은 되살리지는 않지만 다른 방식으로 어긋난다. `useUpdateTask` 의 `onSuccess` 가
목록을 무효화하는데, 토글이 아직 서버에 반영되기 전이라면 재조회가 낙관적 완료
상태를 되돌려 체크박스가 깜빡였다가 토글 응답에 다시 바뀐다.

## 어떻게 막나 — 조합 자체를 만들지 않는다

롤백 로직을 정교하게 만드는 대신 **UI 에서 겹치는 진입을 막는다.** 스냅샷 복원은
"토글 시작 시점으로 되돌린다"는 단순한 계약이라 그대로 두는 편이 낫고, 그 계약이
성립하려면 그 사이에 목록이 다른 이유로 바뀌지 않아야 한다.

| 진행 중 | 잠기는 것 | 열어두는 것 |
|---|---|---|
| 완료 토글 | 편집, 삭제 | 체크박스 (아래 참조) |
| 삭제 | 체크박스, 편집, 삭제 | — |

## 진행 중 여부를 state 로 두지 않는 이유

`useTogglingTaskIds` 는 별도 state 없이 TanStack Query 의 pending 뮤테이션에서
대상 id 를 파생시킨다. 상태를 만들면 해제 시점이 생기고, 해제를 빠뜨리면 버튼이
영구 비활성화된다 — AGENTS.md 하드 룰이 `try/finally` 로 막으라고 명시한 버그
유형이다. 파생 값에는 해제라는 개념 자체가 없어 그 실패 모드가 사라진다.

같은 원리를 `isLatestToggleFor` 가 이미 쓰고 있다 (`isMutating` + `mutationKey`).

비용은 토글 시작·종료마다 목록이 리렌더되는 것인데, 낙관적 업데이트로 어차피
리렌더되므로 실질 추가분은 없다.

## 체크박스를 토글 중에 잠그지 않는 이유

완료→취소 **연타는 의도적으로 지원한다.** `useToggleTask` 의 `isLatestToggleFor`
가드는 먼저 도착한 낡은 응답이 최신 낙관적 상태를 덮어쓰지 못하게 하려고 존재하며,
연타가 불가능해지면 그 가드는 죽은 코드가 된다. 체크박스를 잠그는 것은 이 설계를
되돌리는 결정이므로, 삭제 진행 중일 때만 잠근다.

## 한계

- 같은 태스크를 **다른 탭·기기**에서 동시에 건드리는 경우는 막지 않는다. UI 가드는
  한 클라이언트 안에서만 유효하고, 그 범위의 충돌은 서버가 최종 상태를 정한다
- 편집 모달이 이미 열린 상태에서 다른 기기가 값을 바꾸면 저장 시 덮어쓴다.
  낙관적 잠금(버전 컬럼)이 필요하면 별도 작업으로 다룬다

## 검증

`e2e/task.spec.ts` 의 "완료 토글 응답을 기다리는 동안 편집·삭제가 잠긴다" 가
토글 PATCH 응답을 붙잡아 잠김과 해제를 함께 확인한다. 해제까지 검사하는 이유는
위의 "영구 비활성화" 실패 모드가 회귀하지 않는지 보기 위해서다.
