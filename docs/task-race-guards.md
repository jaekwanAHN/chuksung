# 태스크 토글·삭제·편집

`TaskCard` 한 장에는 같은 태스크를 건드리는 경로가 셋 있다 — 완료 토글, 삭제, 편집.
셋 다 서버 왕복을 하고 그중 토글만 낙관적 업데이트를 쓰기 때문에, 응답이 겹치면
캐시가 사용자의 마지막 의도와 어긋난다.

관련 코드: `src/app/(dashboard)/_hooks/tasks/useTaskMutations.ts`,
`src/app/(dashboard)/_components/tasks/TaskCard.tsx`

## 저장 순서와 화면 반응 (#156·#164)

완료→취소 연타는 계속 허용한다. `TaskCard`마다 `useToggleTask`를 두고
TanStack Query의 `scope.id = toggle-task:<task id>`로 같은 태스크의 PATCH만
직렬 실행한다. 앞선 응답을 받은 뒤 다음 요청을 보내므로, 모든 저장이 성공하면
DB의 최종값과 재조회 결과도 마지막 클릭과 같다. 다른 태스크의 요청은 병렬이다.

대기 중인 mutation도 `onMutate`는 즉시 실행하므로 네트워크 차례를 기다리지 않고
화면이 반응한다. 태스크별 최신 토큰을 첫 await 전에 등록하고, 최신 토큰만 낙관적
화면·성공 응답·롤백·실패 알림을 반영한다. 낡은 성공은 화면을 덮지 않고 마지막 저장
성공 값만 갱신한다. 시간이나 pending 개수로 클릭 순서를 추정하지 않는다.

진행 중인 태스크의 최신 토큰·마지막 저장 성공 값·작업 수는 QueryClient별 WeakMap에
둔다. 필터로 카드가 사라졌다 다시 나타나도 같은 클라이언트의 큐와 복원 기준을
공유하며, 마지막 작업의 `onSettled`에서 해당 항목을 제거한다. 같은 id의 직렬 실행은
Query 자체가 담당하며 별도 Promise 큐를 만들지 않는다.

기존 `isMutating(...) === 1` 판정은 마지막으로 **도착한 응답**만 골랐다. 완료 A →
취소 B를 보내고 B 응답 → A 응답 순서로 받으면 B를 버리고 A를 반영했다. 로컬
`58a9a4b`의 실제 훅을 TypeScript로 변환해 설치된 QueryClient/MutationObserver에
연결하고 HTTP 응답만 제어한 실행에서 최종 캐시 `true`를 재현했다. 브라우저 관측과는
구분되는 훅 콜백 실행 증거다.

## 실패 복원과 알림 계약 (#169)

최신 토글만 실패 알림을 내고 **마지막으로 저장에 성공한 태스크**로 복원한다.
연타 시작 시 캐시 값이 초기 복원 기준이며, 이후 성공 응답이 그 기준을 갱신한다.
직전 클릭의 낙관적 값을 복원 기준으로 쓰면 두 요청이 모두 실패했을 때 저장된 적
없는 값이 남는다.

| 완료 A → 취소 B의 결과 | 최종 화면 | 실패 알림 |
|---|---|---|
| A 성공, B 성공 | B의 취소 | 없음 |
| A 실패, B 성공 | B의 취소 | 없음 |
| A 성공, B 실패 | A의 완료 | B 실패 알림 |
| A 실패, B 실패 | 연타 시작 전 값 | B 실패 알림 |

알림은 `useMutation`의 훅 수준 `onError`에서 최신 토큰을 판정한 뒤 페이지의
`useToast`로 전달한다. `mutate` 호출 옵션의 옵저버 교체 동작에 의존하지 않는다.
이전 구조의 페이지 공용 옵저버는 **다른 태스크를 클릭한 경우에도** 이전 호출의
알림을 생략할 수 있었지만, 이제 최신 여부는 태스크마다 독립적으로 판정한다.

롤백은 해당 id가 목록에 있을 때만 그 항목을 교체한다. 목록 전체 스냅샷을 되돌리지
않으므로 다른 태스크의 저장을 덮거나 삭제된 항목을 되살리지 않는다. 모든 태스크의
토글이 정착할 때 history를 무효화한다. 일반 태스크 목록은 성공 응답으로 갱신해
토글마다 일간 시딩을 포함한 재조회를 만들지 않는다.

## 편집·삭제 잠금과 진행 상태

| 진행 중 | 같은 카드에서 잠기는 것 | 열어두는 것 |
|---|---|---|
| 완료 토글 (큐 대기 포함) | 편집, 삭제 | 체크박스 |
| 삭제 | 체크박스, 편집, 삭제 | — |

`useTogglingTaskIds`는 Query의 pending mutation에서 id 집합을 파생시킨다.
직렬 실행 대기 중에도 pending이므로 마지막 저장이 끝날 때까지 잠금이 유지된다.
성공·실패 후 해제는 Query 수명주기를 따르며 별도 UI 로딩 플래그를 두지 않는다.

같은 태스크의 편집·삭제 잠금은 유지한다. 토글과 편집을 함께 보내면 필드 교체나
목록 재조회가 낙관적 화면을 덮을 수 있고, 삭제와 겹치면 대기 중 PATCH가 사라진
행을 갱신하려 할 수 있기 때문이다.

## 대안과 한계

- 응답 토큰만 추가하면 화면은 지킬 수 있지만 DB 저장 순서는 보장하지 못한다.
  서버 버전 컬럼을 추가하는 대안보다 기존 Query의 태스크별 scope가 이번 보장 범위에
  작고 충분해 선택했다.
- 보장 범위는 하나의 QueryClient에서 시작한 토글이다. 다른 탭·기기, 페이지 전체
  새로고침 전후의 별도 클라이언트 간 동시 쓰기는 서버가 최종 상태를 정한다.
- 서버가 저장한 뒤 응답 연결이 끊긴 경우에는 실패만으로 DB 값을 확정할 수 없다.
  실패 롤백은 클라이언트가 확인한 마지막 성공 값을 기준으로 하며, 모든 저장 성공 시의
  최종값 보장과 구분한다.
- 다른 태스크의 편집·삭제가 만드는 목록 재조회나 외부 재조회와 낙관적 상태의 경합,
  다른 기기의 변경을 편집 모달 저장으로 덮는 문제까지 해결하는 설계는 아니다.

# 템플릿 변경과 일간 목록의 경합

이쪽은 UI 잠금이 아니라 **캐시**의 문제다.

관련 코드: `src/app/(dashboard)/_hooks/templates/useTaskTemplates.ts`,
`src/app/api/task-templates/route.ts`, `src/lib/daily-seed.ts`

## 왜 생겼나

일간 목록은 **GET 자체가 서버에서 템플릿을 시딩하는** 구조라, 응답 내용이 "서버가
그 요청을 처리한 시점"에 좌우된다. 템플릿을 추가하는 순간 이미 일간 GET 이 날아가는
중이면, 그 요청은 새 템플릿이 존재하기 전에 계산된 목록을 들고 돌아온다.

원래 구조는 뮤테이션의 결과("템플릿이 생겼고 오늘 태스크가 시딩됐다")를 **재조회라는
우회 경로로** 받아왔다.

```
POST /api/task-templates → invalidateQueries(daily) → GET /api/tasks?scope=daily
                                                    → 서버가 그 GET 안에서 시딩 → 응답
```

`invalidateQueries` 만 호출하면 재요청이 **진행 중인 요청으로 dedupe** 되어, 그 낡은
응답이 신선한 데이터로 캐시에 안착한다. 방금 추가한 템플릿의 태스크가 `staleTime`(5분)
동안 화면에 나타나지 않는다. PR #65 가 앞에 `cancelQueries` 를 두어 이 창을 닫았다.

## 지금은 어떻게 하나 — 결과를 응답에 싣는다

우회 경로 자체를 없앴다 (#75). 템플릿을 추가·수정한 라우트가 **그 자리에서** 시딩하고,
무엇이 심겼는지를 응답에 담는다.

```
POST /api/task-templates?client_now=...
  → 템플릿 생성 → (시간 게이트 통과 시) 시딩
  → { template, seeded_tasks, target_date }

클라이언트: setQueryData(['tasks','daily',target_date], 기존 목록 + seeded_tasks)
```

- 재조회가 없으니 "재요청이 dedupe 된다"는 경로가 성립하지 않는다
- 왕복이 늘지 않는다. 오히려 재조회 1회가 사라진다
- `applyDailyTemplates` 의 무음 실패가 사용자에게 닿는다 — 시딩이 실패하면
  `seeded_tasks` 가 `null` 로 오고, 클라이언트가 재조회로 복구를 시도한다

**응답에 대상 날짜를 함께 싣는 이유**: 시딩 대상은 "유효 오늘"이라 사용자가 보고 있는
날짜와 다를 수 있고, 캐시 키가 `['tasks','daily',날짜]` 라 정확한 키가 필요하다.

**`seeded_tasks` 가 배열인 이유**: RPC 는 그 날짜에 아직 안 심긴 **활성 템플릿 전부**를
심는다. 방금 만든 것 하나만 담으면 같은 호출에서 함께 심긴 행이 캐시에서 누락된다.

## `cancelQueries` 는 왜 남아 있나 — 역할이 바뀌었다

재조회를 없애도 **뮤테이션 이전에 이미 날아간 조회**는 남는다. 그 응답은 템플릿이
존재하기 전에 계산된 목록이고, 늦게 도착해 `setQueryData` 로 쓴 값을 덮어쓴다.
창이 사라진 게 아니라 모양이 바뀐 것이다.

| | 예전 (#65) | 지금 (#75) |
|---|---|---|
| 무엇을 막나 | 재요청이 진행 중인 요청으로 dedupe 되는 것 | 낡은 응답이 캐시 쓰기를 덮어쓰는 것 |
| 취소 범위 | `['tasks','daily']` 전체 | 시딩 대상 날짜 키 하나 |
| 취소 뒤 | `invalidateQueries` 로 재조회 | `setQueryData` 로 직접 기록 |

`onSuccess` 가 캐시 상태에 따라 셋 중 하나를 고른다.

| 상황 | 처리 | 이유 |
|---|---|---|
| 시딩 결과를 알 수 있음 + 그 날짜 캐시 있음 | 취소 후 `setQueryData` 병합 | 재조회 없이 즉시 반영 |
| 그 날짜 캐시 없음 (첫 로딩 중이거나 다른 날짜를 보는 중) | 취소 후 `invalidateQueries` | 병합할 대상이 없다. 이 재조회는 템플릿 생성 **이후**에 나가므로 서버가 새 템플릿을 본다 |
| `seeded_tasks` 가 `null` (시딩 실패·게이트 미통과) | 취소 후 `invalidateQueries` | 무엇이 심겼는지 모른다 |

**첫 로딩 중에는 취소만 하고 끝내면 안 된다.** 취소는 되돌리기만 할 뿐 재요청을 걸지
않아, 목록이 빈 채로 남는다. 그래서 캐시가 없는 분기에는 반드시 무효화가 따라붙는다.

병합은 서버 정렬(`priority`, `created_at` 오름차순)을 그대로 재현한다. 뒤에 이어
붙이기만 하면 우선순위 1짜리 시딩 태스크가 목록 맨 끝에 붙는다.

## 같은 처리가 템플릿 목록 캐시에도 필요하다

일간 캐시만 보다가 놓쳤던 것이 하나 있다. **템플릿 목록 캐시(`['task-templates']`)도
같은 경합에 노출된다.** 추가 성공 시 `[...prev, created]` 로 무조건 덧붙이고 있었는데,
진행 중이던 목록 조회가 서버의 생성 **이후**에 도착하면 그 응답에 이미 새 템플릿이 들어
있다. 거기에 또 붙이면 같은 항목이 두 벌 남는다.

```
GET /task-templates →                     ← 모달을 열 때 나간 조회
POST /task-templates →                    ← 생성 + 시딩 (원격 왕복 3회)
GET /task-templates ← 200                 ← 새 템플릿이 포함된 목록이 캐시에 안착
onSuccess: [...prev, created]             ← 이미 있는 것을 또 붙인다 → 두 벌
```

전에도 가능했지만 POST 가 시딩까지 하면서 창이 넓어져 **E2E 에서 실제로 재현됐다**
(`template.spec.ts` 의 "템플릿을 추가하면…" 이 같은 제목 두 개를 보고 실패, React 는
같은 key 로 경고). 그래서 목록 쓰기는 덧붙이기가 아니라 **id 기준 upsert** 이고,
취소·폴백을 포함한 세 갈래는 `writeListCache` 하나로 두 캐시가 함께 쓴다.

교훈은 "뮤테이션 응답으로 캐시를 직접 쓰는 곳은 전부 같은 세 갈래가 필요하다"는 것이다.
한쪽만 고치면 다른 쪽에 같은 버그가 남는다.

## 삭제는 왜 아무것도 하지 않나

템플릿 삭제는 일간 목록을 **바꿀 수 없다.** 이미 심긴 태스크는 `tasks` 에 `template_id`
컬럼이 없어 템플릿과 무관하게 남고, 적용 기록만 `ON DELETE CASCADE` 로 함께 사라진다.
템플릿이 없어졌으니 다시 심을 것도 없다. 예전의 무효화는 아무 변화도 없는 목록을
다시 받아오는 왕복이었다.

수정(PATCH)은 다르다. `is_active` false→true 가 실제로 새 시딩을 만들기 때문에 생성과
같은 경로를 탄다. 시딩은 (템플릿, 날짜)당 1회로 멱등하므로, 어떤 필드가 바뀌었는지
라우트가 따로 판정하지 않고 그냥 호출한다 — 그 판정을 두면 RPC 와 어긋날 수 있다.

## 시간 게이트를 한 값으로 줄였다

게이트 판정이 일간 GET 안에만 있었다. 뮤테이션도 같은 판정을 해야 하는데 그대로 두면
둘이 어긋나므로 `src/lib/daily-seed.ts` 로 뽑았고, 그 과정에서 두 조건이 하나로 줄었다.

```
예전: targetDate >= 유효오늘  &&  clientNow >= `${targetDate}T${시작시각}`
지금: targetDate === 유효오늘
```

동치다. 네 경우로 나뉜다.

| targetDate | 결과 |
|---|---|
| 유효 오늘 = 달력 오늘 (지금이 시작시각 이후) | `clientNow >= 오늘T시작시각` 이 참 → 통과 |
| 유효 오늘 = 달력 어제 (지금이 시작시각 이전) | `clientNow`(오늘) `>= 어제T시작시각` 이 항상 참 → 통과 |
| 유효 오늘보다 미래 | `clientNow` 가 그 날짜의 시작시각에 아직 못 미친다 → 차단 |
| 유효 오늘보다 과거 | 첫 조건에서 차단 |

즉 두 조건이 함께 잘라내던 것은 처음부터 "유효 오늘이 아닌 날짜"였다. 한 값으로 줄이면
GET 과 뮤테이션이 **어긋날 수단 자체가 없어진다.**

프로필(`day_start_time`) 조회를 아끼던 최적화는 `isSeedCandidateDate` 로 남겼다. 시딩
대상은 언제나 달력 오늘 아니면 달력 어제라, 그 둘이 아니면 원격 왕복 없이 잘라낸다.

## 회귀 방지

`e2e/template.spec.ts` 의 **"진행 중인 일간 조회가 있어도 방금 추가한 템플릿이 즉시
반영된다"** 가 순서를 코드로 고정한다. 지연을 요청 전송이 아니라 **응답 전달**에만
걸어야 한다 — 서버 전송을 늦추면 서버가 템플릿 생성 이후에 목록을 계산해 경합이
성립하지 않는다.

**같은 파일의 "템플릿을 추가하면…" 테스트로는 부족하다.** 그쪽도 가드를 지우면 실패할
때가 있지만, 진행 중인 GET 이 있느냐가 실제 타이밍에 달려 있어 **통과해 버리는 실행이
있다**(2026-08-13 실측). 탐지기로는 신뢰할 수 없다.

### 예전 구조에서 재현한 기록

2026-08-13, `cancelQueries` 한 줄이 실제로 일하는지 순서를 강제하는 하네스로 확인했다.
아래는 재조회 기반 구조에서의 관측이다.

```
+1619ms  GET daily →
+2016ms  서버가 낡은 목록 계산 완료      ← 템플릿 없는 상태
+2349ms  POST template →
+2636ms  낡은 응답 전달
+2647ms  GET daily ← 200                 ← 재요청이 dedupe 되어 낡은 응답이 안착
         시딩 태스크: 화면에 없음
```

이 경합에서는 시딩이 **아예 일어나지 않았다.** 템플릿 생성 이후에 서버로 가는 GET 이
없었기 때문이다. 증상은 "태스크가 늦게 보인다"가 아니라 "그날 시딩이 통째로 누락된다"에
가깝다. 지금 구조에서는 POST 자체가 시딩하므로 이 실패 모드가 남지 않는다.

# 동시 시딩 요청 — DB 가 중재한다

앞의 두 절은 한 브라우저 안의 문제였다. 이쪽은 **서버로 겹쳐 들어오는 요청**이라
클라이언트 가드가 닿지 않는다. 중재는 DB 제약이 한다.

관련 코드: `supabase/migrations/0009_seed_daily_templates_rpc.sql`,
`supabase/migrations/20260826022206_seed_daily_templates_returns_rows.sql`,
`src/lib/apply-daily-templates.ts`, `src/lib/daily-seed.ts`,
`src/app/api/tasks/route.ts`

## 겹침은 예외가 아니라 상시 상태다

시딩 진입점은 둘이다 — **일간 목록 GET 의 부수효과**(그날 첫 접속)와 **템플릿
추가·수정 라우트**(그 자리에서 심고 결과를 응답에 싣는다). 목록을 조회하는 행위
자체가 시딩을 일으키므로, 아래는 전부 정상 사용 중에 발생한다.

- 탭 두 개를 같은 날짜로 열어 둠
- 하루 시작 시각 직후 재조회와 사용자의 새로고침이 겹침
- 느린 응답에 새로고침 연타
- 템플릿을 추가하는 POST 의 시딩과 진행 중인 일간 GET 의 시딩이 겹침

## 무엇이 중재하나

`task_template_applications` 의 `UNIQUE (template_id, applied_date)` 다.
"이 템플릿을 이 날짜에 이미 심었다"를 기록하는 장부이고, 제약이 중복 행을 막는다.

RPC 는 그 제약 위에서 **한 SQL 문**으로 선점과 삽입을 묶는다.

```sql
with claimed as (
  insert into task_template_applications (...)
  ... on conflict (template_id, applied_date) do nothing
  returning template_id            -- ← 이번 호출이 "새로" 따낸 것만
)
insert into tasks (...) select ... join claimed c on c.template_id = t.id
```

**`returning` 이 이 설계의 심장이다.** 묻는 것이 "장부에 행이 있나"가 아니라
"이번 호출에서 내가 새로 넣은 행이 무엇인가"다. 경쟁에서 진 호출은 빈손이 되고
태스크를 하나도 만들지 않는다.

## 깨지는 방식 — 제약이 아니라 `returning` 을 잃는다

가장 그럴듯한 회귀는 성능·가독성을 이유로 CTE 를 두 문장으로 쪼개면서, 두 번째
문장이 `returning` 대신 **장부를 재조회**하게 되는 것이다.

```
호출 A                          호출 B
────────────────────────────────────────────────────────
장부에 선점 insert  ✓
                                장부에 선점 insert  ✗ (UNIQUE 충돌 → 무시)
장부 재조회 → "있음"             장부 재조회 → "있음"   ← B 도 있다고 본다
tasks insert ✓                  tasks insert ✓        ← 중복
```

`UNIQUE` 제약은 **여전히 제 일을 한다** — 장부에는 한 행만 남는다. 그런데 태스크는
두 개가 생긴다. 제약이 지키는 것은 장부이지 태스크가 아니다.

READ COMMITTED 에서 각 문장은 새 스냅샷을 뜨므로, 진 쪽의 재조회는 이긴 쪽이
커밋한 행을 본다. 즉 **한 트랜잭션 안에 있어도 두 문장으로 나뉘는 순간 이 창이 열린다.**

**사용자 눈에는** 일간 목록에 같은 항목이 두 개, 세 개로 보인다. `tasks` 에는
`template_id` 컬럼이 없어 어느 것이 중복 시딩인지 사후에 구분할 수단도 없다.
게다가 이 RPC 는 원래 CI e2e 의 간헐 실패(flake)를 없애려고 만든 것이라, 회귀하면
증상이 다시 "가끔 깨진다"로 돌아온다 — 재현이 안 돼 가장 진단하기 어려운 형태다.

## 주석의 "단일 트랜잭션" 은 무엇을 막는가

마이그레이션 주석은 "단일 문 = 단일 트랜잭션이라 부분 실패 창이 없다"고 적어 뒀다.
엄밀히는 **Postgres 함수는 문장을 몇 개로 쪼개든 호출 전체가 한 트랜잭션**이라,
함수 안에서 나눠도 "선점만 커밋되고 태스크는 안 생기는" 상태는 만들어지지 않는다.

그 문장이 실제로 대비하는 것은 **로직이 앱 쪽 다중 왕복으로 되돌아가는 것**
(0009 이전 구조)이다. 그쪽에는 진짜 창이 있었다. 위험한 회귀는 부분 실패가 아니라
바로 앞 절의 **중복 생성**이고, 아래 테스트가 겨누는 것도 그쪽이다.

## 회귀 방지

`e2e/seeding-race.spec.ts` 가 시딩 RPC 를 `Promise.all` 로 5회 동시 호출하고
**템플릿당 태스크가 정확히 1개**인지 확인한다. 장부 행 수와 재호출 멱등성도 함께 본다
(태스크만 보면 `UNIQUE` 가 사라져도 우연히 통과할 수 있다).

설계상 짚어 둘 것이 셋 있다.

| 결정 | 이유 |
|---|---|
| **`workers` 를 늘리지 않는다** | `playwright.config.ts` 의 `workers: 1` 은 단일 테스트 계정 보호용이다. 워커 병렬화는 동시성 테스트가 아니라 테스트끼리 서로를 깨뜨리는 것이 된다. 동시성은 **한 테스트 안의 `Promise.all`** 로 만든다 |
| **라우트가 아니라 RPC 를 직접 부른다** | 검증 대상인 주장이 전부 RPC 안에 있고, 라우트를 거치면 아래의 시간 게이트가 미래 날짜를 막는다. 라우트→시딩 배선은 `template.spec.ts` 가 덮는다 |
| **먼 미래 날짜(`2099-12-31`)** | 시딩은 진짜 `tasks` 행을 만든다. 오늘 날짜로 쏘면 사용자의 실제 목록에 나타나고 `pnpm perf`의 데이터 볼륨도 흔든다 (`docs/perf/incidents/data-volume-contamination.md`) |

정리는 `finally` 에서 하되 **날짜가 아니라 우리가 만든 제목·템플릿 id 기준**으로
지운다 — 다른 실행과 날짜가 겹쳐도 서로를 지우지 않는다. 적용 기록은
`template_id` 의 `ON DELETE CASCADE` 로 템플릿과 함께 사라진다.

### 라우트로는 미래 날짜를 시딩할 수 없다

`@/lib/daily-seed` 의 게이트는 두 조건을 함께 건다.

```
targetDate === 유효오늘(clientNow, day_start_time)      (시딩 게이트)
|Date.parse(clientNow+':00Z') - Date.now()| <= 24h      (isTrustableClientNow)
```

첫 번째가 시딩 가능한 날짜를 `clientNow` 기준 오늘·어제로 못 박으므로, 미래 날짜 D 를
심으려면 `client_now` 를 D 로 보내야 한다. 그러면 두 번째가 그것을 자른다 — `D T06:00Z
<= now + 24h` 여야 하고, 이는 **실행 시각의 UTC 시(hour)가 6 이상일 때만** 참이다.
라우트로 내일 날짜를 겨누면 오후에는 통과하고 오전에는 막히는, 그 자체가 flake 인
테스트가 된다. RPC 를 직접 부르는 두 번째 이유가 이것이다.

(게이트를 두 조건에서 한 조건으로 줄인 것은 등가 변환이라 이 상한도 그대로다 —
위쪽 「시간 게이트를 한 값으로 줄였다」 참조.)
