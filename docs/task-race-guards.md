# 태스크 토글·삭제·편집

`TaskCard` 한 장에는 같은 태스크를 건드리는 경로가 셋 있다 — 완료 토글, 삭제, 편집.
셋 다 서버 왕복을 하고 그중 토글만 낙관적 업데이트를 쓰기 때문에, 응답이 겹치면
캐시가 사용자의 마지막 의도와 어긋난다.

관련 코드: `src/app/(dashboard)/_hooks/tasks/useTaskMutations.ts`,
`src/app/(dashboard)/_components/tasks/TaskCard.tsx`

## 왜 막아야 하나 — 삭제된 항목이 되살아나는 경로

토글은 `onMutate` 에서 **리스트 전체 배열**의 스냅샷을 잡고, 실패하면 `onError` 가
그 배열을 통째로 되돌린다. 스냅샷은 토글이 시작된 시점의 목록이다.

```
1. 토글 시작 → 스냅샷 [A, B, C] 저장, 낙관적으로 A 를 완료로 표시
2. 응답 대기 중 B 삭제 성공 → 캐시 [A, C]
3. 토글 실패 → onError 가 스냅샷 복원 → 캐시 [A, B, C]
                                              ↑ 삭제된 B 가 되살아난다
```

되살아나는 것은 **실패 롤백** 경로다. 성공 경로(`onSuccess`)는 `map` 으로 해당
항목만 교체하므로 이미 사라진 항목에는 아무 영향이 없다.

반대 방향도 같다. 삭제 응답을 기다리는 동안 토글을 걸면 위와 같은 조합이 만들어진다.

편집은 되살리지는 않지만 다른 방식으로 어긋난다. `useUpdateTask` 의 `onSuccess` 가
목록을 무효화하는데, 토글이 아직 서버에 반영되기 전이라면 재조회가 낙관적 완료
상태를 되돌려 체크박스가 깜빡였다가 토글 응답에 다시 바뀐다.

## 어떻게 막나 — 조합 자체를 만들지 않는다

롤백 로직을 정교하게 만드는 대신 **UI 에서 겹치는 진입을 막는다.** 스냅샷 복원은
"토글 시작 시점으로 되돌린다"는 단순한 계약이라 그대로 두는 편이 낫고, 그 계약이
성립하려면 그 사이에 목록이 다른 이유로 바뀌지 않아야 한다.

| 진행 중 | 잠기는 것 | 열어두는 것 |
|---|---|---|
| 완료 토글 | 편집, 삭제 | 체크박스 (아래 참조) |
| 삭제 | 체크박스, 편집, 삭제 | — |

## 진행 중 여부를 state 로 두지 않는 이유

`useTogglingTaskIds` 는 별도 state 없이 TanStack Query 의 pending 뮤테이션에서
대상 id 를 파생시킨다. 상태를 만들면 해제 시점이 생기고, 해제를 빠뜨리면 버튼이
영구 비활성화된다 — AGENTS.md 하드 룰이 `try/finally` 로 막으라고 명시한 버그
유형이다. 파생 값에는 해제라는 개념 자체가 없어 그 실패 모드가 사라진다.

같은 원리를 `isLatestToggleFor` 가 이미 쓰고 있다 (`isMutating` + `mutationKey`).

비용은 토글 시작·종료마다 목록이 리렌더되는 것인데, 낙관적 업데이트로 어차피
리렌더되므로 실질 추가분은 없다.

## 체크박스를 토글 중에 잠그지 않는 이유

완료→취소 **연타는 의도적으로 지원한다.** `useToggleTask` 의 `isLatestToggleFor`
가드는 먼저 도착한 낡은 응답이 최신 낙관적 상태를 덮어쓰지 못하게 하려고 존재하며,
연타가 불가능해지면 그 가드는 죽은 코드가 된다. 체크박스를 잠그는 것은 이 설계를
되돌리는 결정이므로, 삭제 진행 중일 때만 잠근다.

## 한계

- 같은 태스크를 **다른 탭·기기**에서 동시에 건드리는 경우는 막지 않는다. UI 가드는
  한 클라이언트 안에서만 유효하고, 그 범위의 충돌은 서버가 최종 상태를 정한다
- 편집 모달이 이미 열린 상태에서 다른 기기가 값을 바꾸면 저장 시 덮어쓴다.
  낙관적 잠금(버전 컬럼)이 필요하면 별도 작업으로 다룬다

## 검증

`e2e/task.spec.ts` 의 "완료 토글 응답을 기다리는 동안 편집·삭제가 잠긴다" 가
토글 PATCH 응답을 붙잡아 잠김과 해제를 함께 확인한다. 해제까지 검사하는 이유는
위의 "영구 비활성화" 실패 모드가 회귀하지 않는지 보기 위해서다.

# 템플릿 변경과 일간 목록의 경합

이쪽은 UI 잠금이 아니라 **캐시**의 문제다.

관련 코드: `src/app/(dashboard)/_hooks/templates/useTaskTemplates.ts`

## 왜 생기나

일간 목록은 **GET 자체가 서버에서 템플릿을 시딩하는** 구조라, 응답 내용이 "서버가
그 요청을 처리한 시점"에 좌우된다. 템플릿을 추가하는 순간 이미 일간 GET 이 날아가는
중이면, 그 요청은 새 템플릿이 존재하기 전에 계산된 목록을 들고 돌아온다.

이때 `invalidateQueries` 만 호출하면 재요청이 **진행 중인 요청으로 dedupe** 되어,
그 낡은 응답이 신선한 데이터로 캐시에 안착한다. 방금 추가한 템플릿의 태스크가
`staleTime`(5분) 동안 화면에 나타나지 않는다.

`invalidateToday` 가 `invalidateQueries` 앞에 `cancelQueries` 를 두는 이유가 이것이다
(PR #65). 진행 중인 요청을 먼저 끊어야 새 요청이 실제로 나간다.

## 그 한 줄이 실제로 일하는지 확인했다

2026-08-13, 순서를 강제하는 하네스로 재현했다. 지연을 요청 전송이 아니라 **응답
전달**에만 걸어야 한다 — 서버 전송을 늦추면 서버가 템플릿 생성 이후에 목록을 계산해
경합이 성립하지 않는다.

**`cancelQueries` 없이** — 낡은 응답이 캐시에 안착한다.

```
+1619ms  GET daily →
+2016ms  서버가 낡은 목록 계산 완료      ← 템플릿 없는 상태
+2349ms  POST template →
+2636ms  낡은 응답 전달
+2647ms  GET daily ← 200                 ← 재요청이 dedupe 되어 낡은 응답이 안착
         시딩 태스크: 화면에 없음
```

**현재 코드** — 취소된 쿼리라 안착하지 못한다.

```
+2372ms  POST template →
+2570ms  GET daily →                     ← 취소 후 새 요청이 실제로 나감
+2684ms  낡은 응답 전달                  ← 버려진다
+2928ms  GET daily ← 200                 ← 신선한 응답
         시딩 태스크: 표시됨
```

이 경합에서는 시딩이 **아예 일어나지 않는다.** 템플릿 생성 이후에 서버로 가는 GET 이
없기 때문이다. 그래서 증상은 "태스크가 늦게 보인다"가 아니라 "그날 시딩이 통째로
누락된다"에 가깝다.

## 회귀 방지

`e2e/template.spec.ts` 의 **"진행 중인 일간 조회가 있어도 방금 추가한 템플릿이 즉시
반영된다"** 가 위 순서를 그대로 재현한다. `cancelQueries` 를 지우면 이 테스트가 실패한다.

**같은 파일의 "템플릿을 추가하면…" 테스트로는 부족하다.** 그쪽도 가드를 지우면 실패할
때가 있지만, 진행 중인 GET 이 있느냐가 실제 타이밍에 달려 있어 **통과해 버리는 실행이
있다**(실측으로 확인). 탐지기로는 신뢰할 수 없다 — 순서를 코드로 고정한 쪽이 필요하다.

## 남은 것

`applyDailyTemplates` 는 best-effort 라 시딩 실패를 삼키고 `console.error` 만 남긴다.
사용자에게는 "템플릿이 그날 안 들어온" 것으로만 보인다. 뮤테이션 응답에 시딩 결과를
담는 구조 변경(#75)이 이 무음도 함께 없앨 수 있다.

# 동시 시딩 요청 — DB 가 중재한다

앞의 두 절은 한 브라우저 안의 문제였다. 이쪽은 **서버로 겹쳐 들어오는 요청**이라
클라이언트 가드가 닿지 않는다. 중재는 DB 제약이 한다.

관련 코드: `supabase/migrations/0009_seed_daily_templates_rpc.sql`,
`src/lib/apply-daily-templates.ts`, `src/app/api/tasks/route.ts`

## 겹침은 예외가 아니라 상시 상태다

시딩은 **일간 목록 GET 의 부수효과**다 (`route.ts` 의 시간 게이트 통과 시
`applyDailyTemplates` 호출). 목록을 조회하는 행위 자체가 시딩을 일으키므로,
아래는 전부 정상 사용 중에 발생한다.

- 탭 두 개를 같은 날짜로 열어 둠
- 하루 시작 시각 직후 재조회와 사용자의 새로고침이 겹침
- 느린 응답에 새로고침 연타
- 템플릿 추가로 일간 목록을 무효화했는데 이전 조회가 아직 진행 중

## 무엇이 중재하나

`task_template_applications` 의 `UNIQUE (template_id, applied_date)` 다.
"이 템플릿을 이 날짜에 이미 심었다"를 기록하는 장부이고, 제약이 중복 행을 막는다.

RPC 는 그 제약 위에서 **한 SQL 문**으로 선점과 삽입을 묶는다.

```sql
with claimed as (
  insert into task_template_applications (...)
  ... on conflict (template_id, applied_date) do nothing
  returning template_id            -- ← 이번 호출이 "새로" 따낸 것만
)
insert into tasks (...) select ... join claimed c on c.template_id = t.id
```

**`returning` 이 이 설계의 심장이다.** 묻는 것이 "장부에 행이 있나"가 아니라
"이번 호출에서 내가 새로 넣은 행이 무엇인가"다. 경쟁에서 진 호출은 빈손이 되고
태스크를 하나도 만들지 않는다.

## 깨지는 방식 — 제약이 아니라 `returning` 을 잃는다

가장 그럴듯한 회귀는 성능·가독성을 이유로 CTE 를 두 문장으로 쪼개면서, 두 번째
문장이 `returning` 대신 **장부를 재조회**하게 되는 것이다.

```
호출 A                          호출 B
────────────────────────────────────────────────────────
장부에 선점 insert  ✓
                                장부에 선점 insert  ✗ (UNIQUE 충돌 → 무시)
장부 재조회 → "있음"             장부 재조회 → "있음"   ← B 도 있다고 본다
tasks insert ✓                  tasks insert ✓        ← 중복
```

`UNIQUE` 제약은 **여전히 제 일을 한다** — 장부에는 한 행만 남는다. 그런데 태스크는
두 개가 생긴다. 제약이 지키는 것은 장부이지 태스크가 아니다.

READ COMMITTED 에서 각 문장은 새 스냅샷을 뜨므로, 진 쪽의 재조회는 이긴 쪽이
커밋한 행을 본다. 즉 **한 트랜잭션 안에 있어도 두 문장으로 나뉘는 순간 이 창이 열린다.**

**사용자 눈에는** 일간 목록에 같은 항목이 두 개, 세 개로 보인다. `tasks` 에는
`template_id` 컬럼이 없어 어느 것이 중복 시딩인지 사후에 구분할 수단도 없다.
게다가 이 RPC 는 원래 CI e2e 의 간헐 실패(flake)를 없애려고 만든 것이라, 회귀하면
증상이 다시 "가끔 깨진다"로 돌아온다 — 재현이 안 돼 가장 진단하기 어려운 형태다.

## 주석의 "단일 트랜잭션" 은 무엇을 막는가

마이그레이션 주석은 "단일 문 = 단일 트랜잭션이라 부분 실패 창이 없다"고 적어 뒀다.
엄밀히는 **Postgres 함수는 문장을 몇 개로 쪼개든 호출 전체가 한 트랜잭션**이라,
함수 안에서 나눠도 "선점만 커밋되고 태스크는 안 생기는" 상태는 만들어지지 않는다.

그 문장이 실제로 대비하는 것은 **로직이 앱 쪽 다중 왕복으로 되돌아가는 것**
(0009 이전 구조)이다. 그쪽에는 진짜 창이 있었다. 위험한 회귀는 부분 실패가 아니라
바로 앞 절의 **중복 생성**이고, 아래 테스트가 겨누는 것도 그쪽이다.

## 회귀 방지

`e2e/seeding-race.spec.ts` 가 시딩 RPC 를 `Promise.all` 로 5회 동시 호출하고
**템플릿당 태스크가 정확히 1개**인지 확인한다. 장부 행 수와 재호출 멱등성도 함께 본다
(태스크만 보면 `UNIQUE` 가 사라져도 우연히 통과할 수 있다).

설계상 짚어 둘 것이 셋 있다.

| 결정 | 이유 |
|---|---|
| **`workers` 를 늘리지 않는다** | `playwright.config.ts` 의 `workers: 1` 은 단일 테스트 계정 보호용이다. 워커 병렬화는 동시성 테스트가 아니라 테스트끼리 서로를 깨뜨리는 것이 된다. 동시성은 **한 테스트 안의 `Promise.all`** 로 만든다 |
| **라우트가 아니라 RPC 를 직접 부른다** | 검증 대상인 주장이 전부 RPC 안에 있고, 라우트를 거치면 아래의 시간 게이트가 미래 날짜를 막는다. 라우트→시딩 배선은 `template.spec.ts` 가 덮는다 |
| **먼 미래 날짜(`2099-12-31`)** | 시딩은 진짜 `tasks` 행을 만든다. 오늘 날짜로 쏘면 사용자의 실제 목록에 나타나고 `pnpm perf` 의 데이터 볼륨도 흔든다 (`docs/perf/README.md` 의 2026-07-27 사건) |

정리는 `finally` 에서 하되 **날짜가 아니라 우리가 만든 제목·템플릿 id 기준**으로
지운다 — 다른 실행과 날짜가 겹쳐도 서로를 지우지 않는다. 적용 기록은
`template_id` 의 `ON DELETE CASCADE` 로 템플릿과 함께 사라진다.

### 라우트로는 미래 날짜를 시딩할 수 없다

`route.ts` 의 시간 게이트는 두 조건을 함께 건다.

```
clientNow >= `${targetDate}T${startTime}`               (시딩 게이트)
|Date.parse(clientNow+':00Z') - Date.now()| <= 24h      (isTrustableClientNow)
```

두 번째가 첫 번째의 상한을 자른다. 날짜 D 를 시딩하려면 `D T06:00Z <= now + 24h`
여야 하고, 이는 **실행 시각의 UTC 시(hour)가 6 이상일 때만** 참이다. 라우트로
내일 날짜를 겨누면 오후에는 통과하고 오전에는 막히는, 그 자체가 flake 인 테스트가
된다. RPC 를 직접 부르는 두 번째 이유가 이것이다.
