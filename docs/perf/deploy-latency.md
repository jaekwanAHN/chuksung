# 배포 URL 지연 측정

로컬 `pnpm perf` 와 별개로, **배포된 프로덕션 URL** 의 서버 응답 지연(TTFB)을
인증 상태로 측정한 기록. 측정 지점은 한국(사용자 실제 위치)이다.
최신 측정이 위에 온다. **지난 섹션은 고치지 않는다** — 그 시점의 기록이다.

## 왜 별도 측정이 필요했나

`pnpm perf` 는 로컬 빌드를 로컬 Chrome 으로 측정한다(`docs/perf/README.md`).
함수와 DB 가 같은 머신에 있으므로 **네트워크 거리 비용이 0 으로 고정**된다.
실제로 원장(`history.md`)의 최신 기록은 `/daily` Perf 95 · LCP 2.39s 로 양호했지만,
같은 시점 배포 환경에서는 인증 API 하나가 1초를 썼다.

> 로컬에서만 재는 하네스는 배포 환경의 지연을 영원히 보지 못한다.
> `history.md` 의 볼륨 경고와 같은 계열의 맹점이다.

## 방법

- `scripts/perf/auth.mjs` 의 `getAuthCookieHeader()` 로 E2E 테스트 계정 세션 쿠키를
  발급해 `Cookie` 헤더로 주입 (Lighthouse 측정과 동일한 방식)
- 경로별 7회 요청. **1회차는 cold 로 따로 기록**하고 나머지 6회의 median 을 채택
- 리다이렉트는 따라가지 않는다(`redirect: 'manual'`) — 리다이렉트 자체의 비용을 재기 위해
- **쓰기 부작용이 있는 경로는 측정하지 않는다.** `/api/tasks` 의 `daily` 스코프는
  `client_now` 로 템플릿 시딩(INSERT)을 유발하므로 `weekly` 로 대체했다.
  측정이 데이터 볼륨을 바꾸면 이후 모든 비교가 오염된다

# 2026-08-13 · 루트 `/` 분기의 프록시 이동 (#91)

`/` 의 로그인 분기를 `app/page.tsx` 에서 프록시로 올렸다. 프록시가 이미 계산한
판단을 페이지 함수가 `getUser()` 로 다시 묻던 것을 없앤다.

## 성공 신호: 페이지 함수가 뜨지 않는다

`x-vercel-id` 의 세그먼트 수가 그대로 드러낸다. 1 개면 프록시가 끝낸 것이고,
2 개면 페이지 함수가 떴다는 뜻이다.

```
before  /  307  x-vercel-id: icn1::icn1::7ml9r-…   세그먼트 2
after   /  307  x-vercel-id: icn1::598vm-…         세그먼트 1
```

## 결과 (median, warm)

| 경로 | before | after | 델타 |
|---|---|---|---|
| 정적 파일 (대조군) | 14ms | 13ms | 회선 상태 동등 |
| `/login` 비인증 (200, 페이지 함수 기동) | 146ms | 128ms | (—) |
| `/login` 인증 (307, **순수 프록시**) | — | **126ms** | 기준점 |
| **`/` (인증 → `/daily`)** | **178ms** | **115ms** | 🟢 **-63ms (-35%)** |
| `/daily` (SSR 셸) | 222ms | 273ms | ⚠️ 잡음 |

cold: `/` 904ms → 130ms.

## 읽는 법

- **세로가 아니라 가로로 읽어야 하는 측정이다.** 같은 회차의 순수 프록시 비용이
  126ms 인데 `/` 가 115ms 다. **`/` 는 이제 프록시 비용 그 자체이고, 페이지 함수
  가산분이 사라졌다.** before 에서는 프록시 비용(#90 기록 106ms) 위에 70ms 가량이
  얹혀 있었다.
- **`/daily` 가 나빠진 것은 이 변경과 무관하다.** `/daily` 는 리다이렉트가 아니라
  통과 경로라 코드가 그대로다. 대조군이 동등한데도 흔들리는 걸 보면 SSR 응답
  자체의 회차 변동이다. 이 항목은 델타로 읽지 말 것.
- **이득은 세션당 한 번이다.** `/` 진입은 북마크·주소창 입력에서만 일어난다.
  #90 이 모든 요청에 걸렸던 것과 규모가 다르다 — 이 작업의 값어치는 지연 자체보다
  **판단이 두 곳에서 중복되던 구조를 없앤 쪽**에 있다.
- 남은 115ms 는 대부분 `sin1` ↔ 서울 왕복이다. #90 과 같은 벽이고 Hobby 플랜에서는
  코드로 줄일 수 없다.

## 한계

- 위와 동일(단일 지점·TTFB 만·자동화 없음).
- **첫 회차는 진입 엣지가 `kix1`(오사카)로 잡혀 버렸다.** 엣지는 고를 수 없으므로
  before 와 같은 `icn1` 회차가 나올 때까지 다시 쟀다. 버린 회차에서도 `/` 는
  128ms · 세그먼트 1 로 일관됐다.

# 2026-08-11 · 프록시 로컬 JWT 검증 (#90)

프록시의 `getUser()`(Auth 서버 왕복)를 `getClaims()`(JWKS 로 서명 로컬 검증)로 바꿨다.

## 먼저: 프록시는 서울에 없었다

`x-proxy-region` 헤더를 심어 확정했다.

```
x-proxy-region: sin1                                    ← 프록시: 싱가포르
x-vercel-id:    icn1::icn1::mwfmd-…                     ← 페이지·API 함수: 서울
```

`vercel.json` 의 `regions: ["icn1"]` 은 페이지·API 함수에만 적용되고 미들웨어에는
적용되지 않는다(Vercel: "deploys Routing Middleware to all regions … On the Hobby
plan, Routing Middleware runs in fewer regions"). **#88 이후 프록시만 홀로 다른
나라에 남아 있었고, 그 상태로 매 요청 서울의 Auth 서버까지 왕복하고 있었다.**

## 프록시 비용만 격리한 측정

인증 상태로 `/login` 을 치면 프록시가 페이지 함수를 부르지 않고 바로 307 을 낸다
(`x-vercel-id` 세그먼트 1개로 확인). 이 시간은 순수한 프록시 비용이다.

| | median |
|---|---|
| `getUser()` (변경 전) | **~450ms** |
| `getClaims()` (변경 후) | **106ms** |

🟢 **-344ms (-76%)**

## 전 경로 (median, warm)

| 경로 | `icn1` + `getUser` | `icn1` + `getClaims` | 델타 |
|---|---|---|---|
| 정적 파일 (대조군) | 14ms | 120ms | ⚠️ 회선 상태 차이 |
| `/login` (비인증) | 124ms | 137ms | (—) |
| `/` (인증 리다이렉트) | 317ms | **172ms** | 🟢 **-145ms (-46%)** |
| `/daily` (SSR 셸) | 349ms | **134ms** | 🟢 **-215ms (-62%)** |
| `/api/profile` | 111ms | 136ms | (—) |
| `/api/tasks?scope=weekly` | 117ms | **94ms** | (—) |

cold: `/` 966ms, `/daily` 247ms, `/api/tasks` 127ms.

## 읽는 법

- **API 경로가 안 움직인 것이 정상이고, 오히려 검증에 가깝다.** `/api/**` 는 matcher 에서
  제외돼 프록시를 타지 않으므로 이 변경의 영향권 밖이다. **프록시를 타는 경로만
  움직였다** — 변경이 의도한 곳에만 작용했다는 증거다.
- **`/daily` 가 가장 크게 줄었다(-62%).** 프록시 왕복이 크리티컬 패스에 그대로 얹혀
  있던 경로다. 그리고 이 이득은 첫 진입만이 아니라 **모든 클라이언트 내비게이션과
  뷰포트 프리페치**에 적용된다 — 프록시는 그 모든 요청에서 실행되기 때문이다.
- **남은 106ms 는 검증 비용이 아니라 지리다.** 프록시가 `sin1` 에 있는 한 한국
  사용자는 서울↔싱가포르 왕복을 낸다. 코드로 더 줄일 수 없고, Hobby 플랜에서는
  미들웨어 배치를 지정할 수도 없다. **이 항목은 닫힌 게 아니라 막힌 것이다.**
- 대조군(정적 파일)이 14ms → 120ms 로 느려졌다. 이 회차의 회선 상태가 나빴다는
  뜻이므로, 세로 절대값 비교는 신뢰하지 말 것. 같은 회차 안에서 프록시 경로만
  움직였다는 **가로 비교**가 이 측정의 근거다.

## 한계

- 위와 동일(단일 지점·TTFB 만·자동화 없음)에 더해, before/after 가 서로 다른 회차라
  회선 상태 차이가 섞인다. 그래서 프록시 비용을 격리한 측정을 따로 두었다.
- `x-proxy-region` 은 관측 수단일 뿐 제어 수단이 아니다. 값이 바뀌어도 경고는 없다.

# 2026-08-10 · 함수 리전 `iad1` → `icn1` (#88)

## 결과 (median, warm)

| 경로 | `iad1` (before) | `icn1` (after) | 델타 |
|---|---|---|---|
| 정적 파일 (CDN 엣지, 대조군) | 134ms | 14ms | 🟢 -120ms |
| `/login` (SSR, Supabase 미접촉) | 315ms | 124ms | 🟢 **-191ms (-61%)** |
| `/` (인증 리다이렉트) | 1,269ms | 317ms | 🟢 **-952ms (-75%)** |
| `/daily` (SSR 셸) | 482ms | 349ms | 🟢 -133ms (-28%) |
| `/api/profile` (getUser + 1행 조회) | 1,003ms | 111ms | 🟢 **-892ms (-89%)** |
| `/api/tasks?scope=weekly` | 801ms | 117ms | 🟢 **-684ms (-85%)** |

## 결과 (cold, 1회차)

| 경로 | `iad1` | `icn1` |
|---|---|---|
| `/` | 2,051ms | 596ms |
| `/api/profile` | 1,940ms | 285ms |
| `/api/tasks?scope=weekly` | 2,352ms | 136ms |

## 읽는 법

- **`/login` 이 Supabase 를 건드리지 않는데도 315ms 였다**는 점이 진단의 핵심이었다.
  인증 없는 401 응답도 343ms 가 나왔다. DB·플랜과 무관한, 순수한 네트워크 배치 비용이다.
  → **Supabase 무료 플랜은 이 문제의 원인이 아니었다.**
- **API 계열의 개선폭이 가장 크다(-85~89%).** 함수↔Supabase 구간이 태평양 왕복에서
  같은 리전 내 통신으로 바뀌었기 때문이다. `withAuth` 의 `getUser` 와 실제 쿼리가
  각각 왕복하던 것이 사라졌다.
- **`/` 가 여전히 317ms 로 가장 느리다.** 리전 문제가 아니라 구조 문제다.
  프록시가 이미 `user` 를 알고 있는데 `src/app/page.tsx` 가 `getUser` 를 다시 호출한 뒤
  307 로 넘긴다. 이 리다이렉트 체인 제거는 별도 과제다.
- 대조군인 정적 파일까지 빨라진 것은 측정 시점의 회선 상태 차이다.
  절대값이 아니라 SSR/API 와의 **차이**를 보는 용도로만 쓸 것.

## 한계

- 단일 지점(한국)·단일 회선에서의 측정이다. 국외 사용자 관점은 반영되지 않는다.
- before 는 기존 프로덕션, after 는 재배포 직후 프로덕션이다. 코드 차이는
  `vercel.json` 추가뿐이지만 배포 인스턴스가 동일하지는 않다.
- TTFB 만 본다. 렌더링·번들 비용은 `pnpm perf` 쪽 지표에 남는다.
- 이 측정은 아직 자동화돼 있지 않다. 리전이나 Supabase 위치가 바뀌어도
  경고해 줄 장치가 없다 — 배포 URL 측정의 하네스 편입은 남은 과제다.
