# 성능 측정 실행 계약

성능 전후 비교는 **측정 대상·코드·계정·데이터·도구·실행 환경**이 식별되고, 의도한
응답을 실제로 측정했을 때만 성립한다. 경고를 남긴 뒤 숫자를 기록하는 것이 아니라,
신뢰 조건을 통과하지 못하면 기록 자체를 중단하거나 새 기준선으로 격리한다.

## 공통 계약

- 현재 체크아웃의 코드와 원장에 기록한다
- 기본 체크아웃의 perf 전용 자격증명 두 값만 런타임에 빌린다
- E2E 계정으로 폴백하지 않는다
- 저장소 공용 `.perf.lock`으로 세 perf 명령의 동시 실행을 거부한다
- schema v2와 `valid: true`인 스냅샷만 다음 비교 대상으로 선택한다
- 숫자 델타가 성공 기준인 작업에서만 수정 전·후 같은 명령을 실행한다

## 로컬 Lighthouse 신뢰 조건

### 인증과 대상 문서

`signInWithPassword`로 받은 쿠키는 Playwright 브라우저 저장소에 넣고 Lighthouse의
저장소 초기화를 끈다. `extraHeaders.Cookie`로 고정하지 않는다. 그래야 서버가 갱신한
refresh token이 다음 run에도 이어지며, 옛 값으로 덮어써 인증을 끊지 않는다.

매 run에서 다음을 검사한다.

1. `lhr.runtimeError`가 없음
2. `lhr.finalDisplayedUrl`과 요청 URL이 동일함
3. 모든 run이 통과한 뒤에만 스냅샷과 원장을 씀

요청 URL·최종 URL·Lighthouse 버전·개별 지표·적용 audit 가중치(W)를 모든 run에 저장한다.
대표값만 남기면 같은 로그인 화면을 여러 경로에서 잰 사건을 사후 검증할 수 없다.

W는 점수의 분모다. 같은 페이지의 W가 직전 회차와 다르면 그 카테고리(Perf/A11y/SEO) 열은
값만 남기고 델타를 만들지 않는다. 한쪽에 W가 없는 회차는 이 검사를 건너뛴다. 근거는
`README.md` 「적용 audit 가중치(W)」.

### 코드와 실행 환경

스냅샷은 다음 정보를 기록한다.

- git SHA·브랜치·dirty 여부
- `local-production-build` 환경과 앱·Supabase origin
- OS·아키텍처·Node·Chromium·Lighthouse 버전
- 계정 종류와 데이터 볼륨
- 카테고리별 적용 audit 가중치(W)
- 폼팩터·throttling·저장소 초기화 설정·run 수

`--no-build`는 이미 떠 있는 서버의 코드 신원을 확인할 수 없어 원장에 쓰지 않는다.
전후 기록은 각각 현재 체크아웃을 `pnpm build && pnpm start`로 띄운 경로만 사용한다.

비교기는 계정·볼륨·run 수·Lighthouse 버전·백엔드 origin·runner 정보 중 하나라도
다르면 색상 델타를 만들지 않는다. git SHA는 무엇이 달라졌는지를 설명하는 식별자이므로
전후가 다른 것이 정상이다.

## 배포 TTFB 신뢰 조건

- 인증 요청은 응답 `Set-Cookie`를 다음 요청에 반영한다
- 모든 sample에서 경로별 기대 HTTP 상태를 확인한다
- 리다이렉트 경로는 기대 `Location`까지 확인한다
- 프록시를 통과해 헤더가 있는 sample에서 배포 SHA와 프록시 리전이 각각 하나로
  관측돼야 하며, 회차 전체에서 두 값 모두 최소 한 번은 관측돼야 한다
- 정적 자산 대조군·계정·origin·run 수·프록시 리전이 다르면 델타를 만들지 않는다
- runner 플랫폼·아키텍처·Node 버전이 다르면 델타를 만들지 않는다
- 한 회차에서 진입 엣지가 갈리면 그 회차는 이후 델타의 기준선이 되지 않는다

첫 요청은 네트워크 연결과 서버 상태가 함께 섞인 값이다. 서버리스 cold start임을
증명할 수 없으므로 `first`로 기록하고, 나머지의 `repeat median`과 분리한다.

## 작업 브랜치에서 전후 측정

1. 대상 확정 직후 만든 작업 워크트리에서 수정 전 특정 경로를 측정
2. 생성된 원장·스냅샷을 보존
3. 코드를 수정하고 관련 기능을 검증
4. 같은 워크트리·명령·계정·데이터 조건으로 수정 후 측정
5. 두 schema v2 스냅샷과 원장 델타를 함께 커밋

하네스 자체를 고치는 작업은 고장 난 하네스의 전후 숫자를 성공 기준으로 삼지 않는다.
구조·단위 테스트로 차단 조건을 먼저 검증하고, 수정 후 새 신뢰 기준선을 만든다.

## legacy 기록

schema v2 이전 자료는 현재 비교기에서 제외한다. 삭제하지 않고 `archive/`에 보관하되,
활성 원장이나 `snapshots/` 최상위에는 두지 않는다. 알려진 오측정과 단순히 메타데이터가
부족한 legacy를 구분해 `archive/README.md`에 이유를 남긴다.

활성 원장 제목의 시각은 UTC로 표기하며 스냅샷은 ISO 8601 `Z` 시각을 보존한다.

배경 사건:

- `incidents/data-volume-contamination.md`: 서로 다른 데이터셋의 델타
- `incidents/login-page-mismeasurement.md`: 대시보드 대신 로그인 화면 측정

## 남는 한계

- 로컬 머신과 원격 Supabase는 공유 자원이라 측정을 병렬화하지 않는다
- 로컬 lab 지표는 실제 사용자 네트워크·콜드스타트·필드 INP를 대신하지 않는다
- 배포 TTFB는 단일 지점·단일 회선이며 브라우저 렌더링을 보지 않는다
- 로컬 runner 하드웨어 자체는 완전히 고정하지 못하므로 장기 절대값보다 같은 작업의
  가까운 전후 델타가 더 신뢰할 만하다
