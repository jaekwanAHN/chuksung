# D-day 연도 입력 제한 (#184)

2026-10-14 사용자의 “진행해” 응답으로 추가·수정 날짜의 연도 4자리 제한,
관련 검증, 이슈 생성·커밋·푸시·PR 생성까지 승인됐다.
작업 브랜치는 `fix/dday-year-limit`이다.

## 동작과 근거

`b642666`의 D-day 관리 화면은 브라우저 기본 날짜 입력의 값을 그대로 받아
`20267-10-14`처럼 5자리 연도를 표시했다. 수정 전 앱 E2E에서도 같은 값을
입력한 뒤 빈 값이어야 한다는 검사가 실제 `20267-10-14`를 받아 실패했다.

추가·수정 입력 모두 `max="9999-12-31"`로 네이티브 날짜 선택 범위를 제한한다.
이 속성만으로 모든 입력 경로가 차단되지는 않으므로, 변경 이벤트에서도 연도 부분이
4자리를 넘으면 상태에 반영하지 않는다. React의 제어 입력이 이전 값을 복원한다.
빈 값은 허용해 삭제와 입력 중간 상태를 유지한다. API의 기존 `z.iso.date()` 검증과
DB는 변경하지 않는다.

브라우저 기본 날짜 선택 UI를 유지한다. Chromium의 연도 영역은 최대값을 지정하면
네 번째 자리 이후 키 입력을 자체 처리하므로, 추가 키를 눌렀을 때의 정확한 연도 값까지
고정하지 않고 4자리 상한을 검증한다.

## 검증

- 수정 전: 추가 날짜 회귀 E2E가 5자리 값에서 의도대로 실패했다.
- `pnpm test:e2e e2e/dday.spec.ts`: 인증 setup과 D-day 시나리오 2개 모두 통과.
  빈 입력·기존 날짜에 5자리 값 입력, 연도 영역의 키보드 입력, `9999-12-31` 경계,
  입력 지우기, 정상 날짜 추가, 윤년 날짜로 수정 후 저장, 삭제를 확인했다.
- `pnpm lint`: 통과.
- `pnpm build`: 컴파일·타입 검사·페이지 생성 통과. 첫 실행은 Google Fonts 접근
  제한으로 실패했고, 네트워크 권한을 적용한 재실행에서 통과했다.
- `git diff --check`: 통과. 변경된 입력 처리와 테스트를 하드 룰·정확성 기준으로
  직접 검토했고 추가 결함은 발견하지 못했다.

브라우저 검증 범위는 저장소 E2E의 Chromium이다. 전체 E2E와 성능 측정은 공통
탐색·테스트 인프라 변경이나 정량 목표가 없어 실행하지 않았다.
