# 병렬 작업 — 워크트리와 슬롯

**작업은 항상 워크트리에서 한다.** 기본 체크아웃은 브랜치를 따지 않고 늘 main 에 머문다.

```bash
# 기본 체크아웃에서
pnpm wt:preflight              # main 최신화 + 지난 작업의 잔재 보고 (아래 「정리의 주인」)
pnpm wt:new fix/header-date    # 워크트리+브랜치 동시 생성, 부트스트랩, 슬롯 배정
cd .claude/worktrees/fix+header-date
pnpm build                     # 첫 검증은 build 부터 (아래 「부트스트랩」)
# … 작업 · PR · 머지 …

# 다시 기본 체크아웃에서
pnpm wt:rm fix/header-date --delete-branch   # 워크트리+로컬 브랜치 삭제, 슬롯 반납
pnpm wt:ls                                    # 지금 몇 번을 쓰고 있나
```

브랜치는 따로 만들지 않는다 — `wt:new` 가 `git worktree add -b <브랜치> <경로>
origin/main` 로 **디렉터리와 브랜치를 함께** 만든다. 분기 기준은 로컬 main 이 아니라
fetch 한 `origin/main` 이라, 로컬이 뒤처져 있어도 새 워크트리는 최신에서 시작한다.

## 왜 기본 체크아웃에서 작업하지 않나

`git checkout` 은 **하나뿐인 작업 디렉터리를 갈아끼운다.** 두 갈래가 같은 체크아웃에서
브랜치를 오가면 서로의 파일을 갈아엎는다. `git worktree` 는 작업 디렉터리를 하나 더
만들어 두 브랜치가 동시에 펼쳐져 있게 한다 — 병렬 작업에 워크트리가 필요한 이유가
이것이다.

기본 체크아웃을 늘 main 에 두면 부수 효과가 하나 더 있다. **거기서 더티 트리가
발견되면 그 자체가 "뭔가 잘못됐다"는 신호가 된다** — 아무도 거기서 작업하지 않기
때문이다.

## 슬롯이 왜 필요한가

`git worktree` 는 **파일만** 갈라준다. 작업에 필요한 것 중 파일이 아닌 게 둘 있다.

| 자원 | 어디에 있나 | 워크트리가 갈라주나 |
|---|---|---|
| 소스 · `node_modules` · `.next` | 디스크 | 갈라진다 |
| **localhost 포트** | 이 머신에 하나 | 안 갈라진다 |
| **Supabase E2E 테스트 계정** | 원격 DB 에 하나 | 안 갈라진다 |

나누지 않으면 두 가지가 터진다.

**포트 — 조용한 오탐.** `playwright.config.ts` 의 `webServer.reuseExistingServer` 가
로컬에서 `true` 다. 워크트리 둘이 같은 포트를 쓰면 나중 실행이 **먼저 뜬 워크트리의
dev 서버를 그대로 재사용한다.** 에러 없이, 다른 브랜치의 코드를 테스트하고 통과한다.
죽는 실패가 아니라 초록불이 뜨는 실패라 알아채기 어렵다.

**계정 — 무작위 빨간불.** 모든 스펙이 한 계정의 실 DB 를 조작한다. 두 갈래가 동시에
시딩·설정 변경·목록 조작을 하면 서로의 데이터를 지우고 만든다.

**슬롯은 이 둘을 한 세트로 묶은 번호다.**

| 슬롯 | 체크아웃 | 포트 | E2E 계정 | perf |
|---|---|---|---|---|
| 0 | 기본 체크아웃 | 3100 | `E2E_TEST_USER_*` | 여기서만 |
| 1 | 워크트리 | 3101 | `E2E_TEST_USER_*_1` | 불가 |
| 2 | 워크트리 | 3102 | `E2E_TEST_USER_*_2` | 불가 |

슬롯별 값은 그 워크트리의 `.env.local` 에만 쓴다. **스펙 코드는 한 줄도 고치지 않는다**
— 포트도 계정도 이미 환경변수로 갈라져 있다 (`playwright.config.ts`, `e2e/auth.setup.ts`).

## 슬롯을 기록하지 않는 이유

점유 현황을 파일에 적어두지 않는다. **살아 있는 워크트리에서 역산한다** — 각 워크트리
`.env.local` 의 `WT_SLOT` 을 읽어 쓰이는 번호를 모으고, 남은 최소 번호를 준다
(`scripts/worktree/slots.mjs`).

상태 파일을 두면 `pnpm wt:rm` 을 거치지 않은 삭제(손으로 `git worktree remove`,
디렉터리 통째로 삭제)에서 조용히 어긋난다. 어긋난 대장은 있는 번호를 없다고 하거나
없는 번호를 준다. 역산에는 그 실패가 없다 — 디렉터리가 사라지면 번호는 저절로 빈다.

대신 한 가지를 포기했다: **부트스트랩이 안 된 워크트리는 슬롯을 잡지 못한다.**
`.env.local` 이 없으면 `WT_SLOT` 도 없기 때문이다. 그런 워크트리는 어차피 빌드도 E2E 도
못 돌므로 실질적인 손해가 아니고, `pnpm wt:ls` 가 「슬롯 없는 워크트리」로 따로 보여준다.

### 만드는 순간은 잠근다

역산에는 대가가 하나 더 있었다. **임차한 슬롯은 `.env.local` 을 써야 남들에게 보인다.**
그 사이에 `git fetch` 와 `git worktree add` 가 있어 수 초가 비고, `wt:new` 두 개가 그
창에서 만나면 **같은 번호를 집는다.** 실제로 재현됐다 — 빈 슬롯이 하나뿐인데 둘 다
성공해 포트와 계정을 공유했다 (#140).

사람이 터미널 두 개에서 `/work` 를 칠 때는 간격이 벌어져 잘 걸리지 않지만, 자동으로
두 갈래를 동시에 띄우면 정면으로 걸린다 — 그게 이 구조의 목표한 사용 방식이다.

그래서 임차부터 `.env.local` 기록까지를 배타적 잠금(`.claude/worktrees/.repo.lock`,
`open(…, 'wx')`)으로 감싼다. `git fetch` 도 안에 둔다 — 동시 fetch 는
`refs/remotes/origin/main` 잠금 충돌을 낸다. **`pnpm install` 은 밖이다**: 그 시점엔
이미 `.env.local` 이 있어 역산에 잡히고, 수십 초를 잠가둘 이유가 없다.

잠금 파일은 주인의 PID 를 담는다. 프로세스가 죽어 남은 잠금은 `process.kill(pid, 0)`
로 판정해 걷어내므로, 중단된 `wt:new` 가 다음 실행을 영구히 막지 않는다.

**점유의 진실은 여전히 `WT_SLOT` 이다.** 잠금은 만드는 순간만 보호할 뿐, 대장 노릇을
하지 않는다 — 그래야 손으로 지운 워크트리에서도 어긋나지 않는 성질이 남는다.

### 잠금은 하나다

만드는 순간만 잠가서는 부족했다. 기본 체크아웃의 git 상태를 바꾸는 곳이 셋이기
때문이다 — `wt:new` 의 임차, `wt:rm` 의 삭제, `wt:preflight` 의 main 최신화.
셋 다 같은 `refs/remotes/origin/main`·인덱스·워크트리 목록을 건드린다.

용도별로 잠금을 나누면 서로를 보지 못해 다시 겹친다. 그래서 `withRepoLock` 하나로
셋을 상호 배타로 둔다 (`scripts/worktree/slots.mjs`). 겹쳤을 때의 증상은 git 자신의
잠금이 내는 실패다.

```
fatal: Unable to create '.../.git/index.lock': File exists.
```

재시도하면 풀리지만 **메시지가 진짜 실패처럼 보인다.** 특히 `/work` CP0 는 묻지 않고
진행하는 구간이라, 거기서 멈추면 무엇이 잘못됐는지 알기 어렵다 (#142).

**긴 작업은 잠금 밖에 둔다.** `pnpm install` 과 마찬가지로 `gh` 호출도 밖이다 —
`wt:preflight` 는 PR 상태를 다 조회한 뒤에야 잠금을 잡는다. 두 번째 세션이 네트워크
왕복만큼 막히면 병렬화의 의미가 없어진다.

### 잠금은 `link()` 로 건다

처음에는 `open(…, 'wx')` 로 파일을 만들고 PID 를 나중에 썼다. 그런데 그 둘 사이에
**파일이 비어 있는 순간**이 있다. 남이 하필 그때 들여다보면 `JSON.parse` 가 실패하고,
그 실패를 「주인이 죽었다」로 읽어 잠금을 걷어낸 뒤 자기 것을 건다. **둘 다 들어간다.**

경합이 있을 때마다 재현됐다 — 두 프로세스를 동시에 띄우면 매번 같은 밀리초에 함께
진입했다. 잠금이 있는데 아무것도 잠그지 않은 상태였다.

그래서 **내용을 다 쓴 임시 파일을 `link()` 로 건다.** `link` 는 원자적이고 대상이
이미 있으면 `EEXIST` 로 실패하므로, 남에게 보이는 순간 파일에는 이미 PID 가 들어 있다.
빈 창이 사라진다.

두 가지를 함께 바꿨다.

- **읽지 못한 잠금은 살아 있는 것으로 본다.** 정상 경로에 빈 잠금이 없으니, 못 읽었다면
  예외 상황이다. 걷어내면 다시 둘이 들어가므로 시간 초과로 보내 사람이 보게 한다
- **놓을 때도 PID 를 확인한다.** 파일이 우리 것일 때만 지운다 — 남의 잠금을 열어주면
  그 구간이 통째로 무방비가 된다

남은 한계: 주인이 죽어 남은 잠금을 **두 프로세스가 동시에** 걷어내면 여전히 겹칠 수
있다. 잠금을 건 직후 PID 를 되읽어 우리 것이 아니면 다시 기다리므로 창은 마이크로초
수준이고, 애초에 주인이 죽은 뒤에만 열린다. 여기를 완전히 닫으려면 `flock` 이 필요한데
Node 기본 API 에 없다.

**이 잠금은 테스트로 고정되어 있다** (`scripts/worktree/slots.test.mjs`, `pnpm test:unit`,
CI 의 `lint-and-build`). 실패가 조용하기 때문이다 — 둘이 함께 들어가도 에러가 나지 않고,
증상은 몇 단계 뒤에 같은 슬롯을 쓰는 워크트리 둘로만 나타난다. 결정적인 가드는
「읽을 수 없는 잠금은 걷어내지 않는다」이고, 두 프로세스를 띄우는 검사는 결과를 보는
것이라 타이밍에 좌우된다.

## 정리의 주인

**워크트리를 치울 자격이 가장 확실한 것은 그 작업을 한 세션이다.** 7~8번에서 이미
기본 체크아웃으로 나온 뒤이므로 거기서 `pnpm wt:rm <브랜치> --delete-branch` 를
부를 수 있다.

`/work` CP0 는 이것을 대신하지 않는다. **머지 직후에도 그 세션은 아직 살아 있을 수
있기 때문이다** — 정리·보고·후속 확인을 하는 중이다. 그 사이 다른 세션의 CP0 가
「머지됐고 트리가 깨끗하다」는 조건만 보고 지우면 **살아 있는 세션의 작업 디렉터리가
사라진다.** `wt:rm` 의 안전장치(더티 트리·미푸시 커밋)는 여기서 도움이 안 된다 —
머지가 끝난 워크트리는 정의상 깨끗하고 푸시돼 있다.

기계가 확인할 수 있는 것과 없는 것이 갈린다.

| 확인 | 가능? | 수단 |
|---|---|---|
| 브랜치가 머지됐나 | 가능 | `gh pr list --head <브랜치> --state merged` |
| 커밋되지 않은 변경이 있나 | 가능 | `git status --porcelain` |
| 푸시되지 않은 커밋이 있나 | 가능 | `git rev-list` |
| **누가 지금 그 안에 서 있나** | **불가능** | — |

하필 모르는 마지막 하나가 지우기 전에 알아야 할 것이다. 그래서 **판단하는 주체를
사람으로 옮겼다** — 자기가 어떤 세션을 띄워 놨는지는 사람만 안다. `wt:preflight` 는
남은 워크트리를 보고만 하고, 지우는 명령을 출력해 둔다.

주인이 치우면 프리플라이트는 그것을 아예 보지 못한다. 따라서 **거기 보이는 것은 정의상
"주인이 치우지 않은 것"** 이고, 왜 안 치웠는지는 알 필요가 없다. 규칙이 한 줄로 줄어든다.

> 머지된 브랜치의 워크트리가 남아 있으면 → 보고하고 묻는다.

시간 기준도, 점유 프로세스 탐색도 없다. 검토했다가 버린 두 방안이 그것들이었다 —
`/proc/*/cwd` 로 점유 프로세스를 찾기(리눅스 의존이고 셸이 아닌 세션은 못 잡는다),
머지 후 일정 시간이 지난 것만 자동 삭제(기준 시간에 근거가 없다). **추측을 코드에
박는 대신 묻는 편이 낫다.** 주인이 제 몫을 하면 어차피 드물게만 묻게 된다.

**로컬 브랜치는 다르다.** 브랜치는 작업 디렉터리가 아니라 ref 하나라, 지워도 누구의
발밑도 꺼지지 않는다. 워크트리가 잡고 있지 않은 머지된 브랜치는 프리플라이트가
그대로 지운다. 원격 브랜치는 남긴다 — 머지 후에 문제를 발견할 수 있다.

**`wt:rm` 자체는 그대로다.** 사람이 명시적으로 부르는 것은 막을 이유가 없다.

## 부트스트랩 — 무엇을 채우나

`git worktree add` 는 **git 이 추적하는 파일만** 펼친다. gitignore 된 것은 따라오지
않으므로, 갓 만든 워크트리는 소스만 있고 돌아가지는 않는다.

| 없는 것 | 왜 gitignore 인가 | `wt:new` 가 하는 일 |
|---|---|---|
| `.env.local` | service role key · 테스트 계정 비밀번호 | 기본 체크아웃에서 복사 + 슬롯 값으로 치환 |
| `node_modules` | 크기 · 플랫폼 의존 바이너리 | `pnpm install --frozen-lockfile` |
| `.claude/settings.local.json` | 개인 로컬 설정 | 복사 (없으면 넘어감) |
| `next-env.d.ts` | 빌드 산출물 | 아무것도 안 함 — `next build` 가 만든다 |

**gitignore 를 푸는 것은 해결책이 아니다.** service role key 는 RLS 를 통째로 우회하는
키라 히스토리에 한 번 들어가면 재발급 말고는 되돌릴 방법이 없다. 그리고 애초에 필요가
없다 — 이 값들은 이미 이 머신의 기본 체크아웃에 있고, 부트스트랩은 **로컬 안에서 옆으로
복사하는 일**이라 원격이 관여하지 않는다.

Playwright 브라우저 바이너리는 `~/.cache/ms-playwright` 에 있어 머신 전체가 공유한다 —
워크트리마다 다시 받지 않는다.

### 새 워크트리에서는 `pnpm build` 를 먼저 돌린다

`npx tsc --noEmit` 을 먼저 돌리면 실제로 없는 오류가 뜬다.

```
src/app/api/tasks/[id]/route.ts(4,31): error TS2304: Cannot find name 'RouteContext'.
```

`RouteContext` 는 Next 가 `.next/types/` 에 **생성하는** 전역 타입이라 빌드를 한 번도
돌리지 않은 워크트리에는 없다. `pnpm build` 후에는 `tsc` 가 통과한다.

작업은 늘 새 워크트리에서 시작하므로 이 순서 뒤집기는 **매 작업의 첫 검증마다**
해당된다. 두 번째부터는 `.next` 가 있으므로 평소대로 `tsc` 를 먼저 돌리는 게 빠르다.

## 워크트리에 주지 않는 것

`wt:new` 는 `.env.local` 을 복사하면서 두 가지를 **지운다.** 규칙으로 지키는 대신
**닿을 수 없게** 만드는 쪽을 택했다.

**`PERF_TEST_USER_*`** — perf 계정 오염은 몇 주 뒤에야 드러나는 종류의 사고다. 성능
원장의 세로 비교가 그 계정의 데이터 볼륨이 고정되어 있다는 전제 위에 서 있고, 한 번
쓰면 전제가 조용히 깨진다 (`docs/perf/accounts.md`). 값이 없으면 워크트리에서 실수로
perf 를 돌려도 그 계정에 닿지 못한다.

**`SUPABASE_SERVICE_ROLE_KEY`** — RLS 를 통째로 우회하는 키다. 쓰는 곳은
`scripts/e2e/provision-account.mjs` 하나뿐이고, 계정 풀은 기본 체크아웃 `.env.local` 에
등록해야 하므로 프로비저닝은 본래 거기서 하는 작업이다. 워크트리가 늘어날 때마다
사본이 늘어날 이유가 없다.

둘 다 없어서 실패할 때는 각 스크립트가 무엇이 없는지 적어 멈춘다 — 조용히 잘못된
계정을 쓰는 것보다 낫다.

## 직렬로 남긴 것

병렬화하지 않는다. 슬롯을 늘려도 풀리지 않는 것들이다.

| 대상 | 왜 |
|---|---|
| `pnpm perf` | perf 계정 1개 + 원장 파일 1개(`docs/perf/history.md`). 동시 실행이 서로를 덮는다 |
| `pnpm db:push` | 원격 Supabase 프로젝트가 하나. 두 갈래가 동시에 스키마를 바꾸면 충돌한다 |
| 한 프로세스 안의 E2E 워커 | `workers: 1` 유지. 슬롯은 워크트리 *사이*를 가를 뿐, 한 프로세스 안 워커들은 여전히 같은 계정을 공유한다 |
| CI 의 `e2e` job | `concurrency: e2e-shared-account` 유지. CI 병렬화는 별도 과제다 (아래) |

## 계정 풀 만들기

기본 체크아웃 `.env.local` 에 슬롯 수만큼 계정을 둔다.

```bash
pnpm e2e:provision --use slot --email <슬롯1 주소> --email <슬롯2 주소>
```

`scripts/e2e/provision-account.mjs` 가 기준 계정(`E2E_TEST_USER_EMAIL`)의 데이터를
복제해 계정을 만들고, 그대로 붙여넣을 두 줄을 출력한다.

**`--use slot` 을 빠뜨리면 실행되지 않는다.** 같은 스크립트가 perf 계정도 만들기
때문이다 — 용도를 묻지 않고 `PERF_TEST_USER_*` 를 출력하던 시절의 안내를 그대로
따르면 perf 가 E2E 계정을 가리키게 되고, 그 사고는 몇 주 뒤에야 드러난다
(`docs/perf/accounts.md`). `--use perf` 는 perf 계정용이다.

```bash
# 기본 체크아웃 .env.local
E2E_TEST_USER_EMAIL=<기준 계정>          # 슬롯 0
E2E_TEST_USER_PASSWORD=<기준 계정 비번>

E2E_TEST_USER_EMAIL_1=<슬롯 1 계정>       # 워크트리용 풀
E2E_TEST_USER_PASSWORD_1=<슬롯 1 비번>
E2E_TEST_USER_EMAIL_2=<슬롯 2 계정>
E2E_TEST_USER_PASSWORD_2=<슬롯 2 비번>
```

`E2E_TEST_USER_EMAIL_1` 부터 끊길 때까지 세어 풀 크기를 정한다. 즉 **계정을 늘리면
슬롯이 늘어난다.** 풀이 꽉 차면 `wt:new` 가 무엇이 막고 있는지 적어 실패한다.

계정은 실 DB 에 만들어지고 삭제는 Supabase 대시보드 수동이다. 그래서 워크트리마다
새로 만들지 않고 **미리 만들어 돌려쓴다** — 매번 만들면 기준 계정 데이터를 통째로
복제하느라 느리고, 버려진 계정이 쌓인다.

## 남은 과제 — CI 병렬화

CI 의 `e2e` job 은 여전히 전역 직렬이다(`concurrency: e2e-shared-account`). 로컬은
이 문서로 풀렸지만 CI 는 PR→슬롯 매핑과 반납 처리가 필요해 성격이 다르고, 잘못
건드리면 `e2e` 가 required check 라 저장소 전체의 머지가 막힌다. 한계와 전제는
`e2e/README.md` 「데이터 취급 원칙」에 있다.
