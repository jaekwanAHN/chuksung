## 대기 개선

`e2e/task-network.ts`의 `changeTask`는 UI 조작 전에 응답 대기를 등록하고,
변경 요청과 같은 화면 scope의 목록 응답을 구분한다. 변경 응답 이후 도착한 목록을
대상으로 하되, 이미 진행 중이던 최초 조회도 포함한다. 응답 상태와 목록 JSON 수신을
확인한 뒤 기존 DOM assertion으로 실제 반영을 검증한다. 목록에 생성·수정 결과가
없으면 DOM assertion이 실패하므로 오래된 응답을 정상 반영으로 인정하지 않는다.

응답 헤더 대기는 조작 시작부터 최대 15초다. 본문 수신은 전체 테스트 시간 상한을
따른다. 성공 응답 지연과 DOM 갱신 실패를
구분하기 위한 유한한 진단 여유이며 성능 목표나 관측된 최대 지연은 아니다.
DOM assertion의 기본 5초와 전체 테스트 시간 상한은 유지한다.
별도 API polling이나 페이지 새로고침으로 앱의 갱신 실패를 숨기지 않는다.

적용한 네 스펙은 매 테스트에 `api-timing` JSON을 첨부한다. 메서드·경로·scope와
요청 시작·헤더 도착·본문 완료·실패 시각을 기록한다. 쿠키·인증 헤더·요청 및 응답
본문은 기록하지 않는다. 서버 내부 구간 측정은 포함하지 않는다.

## 별도로 재현한 최초 조회 경합

2026-09-16 워크트리 전용 계정에서 임시 Playwright 진단을 실행했다.
아래 순서를 고정해 실제 서버 저장과 화면 누락을 함께 확인했다.

1. `/daily` 최초 `GET /api/tasks`를 `page.route`로 가로채고 `route.fetch()`로
   실제 응답을 확보한 뒤 브라우저에 전달하지 않는다.
2. UI로 고유 제목의 태스크를 생성하고 POST 201 및 모달 닫힘을 기다린다.
3. 보관한 생성 이전 목록을 `route.fulfill({ response })`로 전달한다.
4. 브라우저 목록 GET이 한 번뿐이고 태스크가 표시되지 않는 것을 확인한다.
5. 별도 인증 API 조회에서는 생성한 id가 존재한다. 새로고침하면 화면에도 나타난다.
6. finally에서 진단으로 만든 id만 삭제한다.

진단은 성공했다(인증 setup 포함 2 passed, 10.8초). 잘못된 동작을 성공 조건으로
삼는 임시 스펙은 영구 회귀 테스트로 남기지 않았다.

원인은 `useCreateTask.onSuccess`의 `invalidateQueries`만으로는 진행 중인 최초
조회가 교체되지 않는다는 것이다. 설치된 TanStack Query 5.101.2의 `Query.fetch`는
캐시 데이터가 undefined이면 기존 retryer promise를 재사용한다. 생성 이전 응답이
나중에 도착하면 생성한 태스크가 없는 목록이 캐시에 들어간다. 이는 대기 시간을
늘려도 해결되지 않는 앱 경합이다.

이번 CI의 미완료 GET이 최종적으로 오래된 결과를 반환했는지는 trace 종료 이후라
알 수 없다. 따라서 CI 실패 전부를 이 경합 탓으로 단정하지 않는다. 삭제 후 GET
지연과 최초 조회 경합은 구분한다. 일간 GET은 인증, 프로필 조회, 시딩 RPC, 목록
조회를 순차 수행하므로 지연 후보가 여럿이며 추가 서버 측 관측 없이는 구간별
원인을 확정할 수 없다.

앱 수정 후보는 생성 성공 때 대상 쿼리를 명시적으로 취소하고 재조회하거나,
취소 후 생성 결과를 캐시에 반영하는 것이다. 이번 변경은 E2E 대기·진단에 한정한다.

## 로컬 회귀 검증 중 추가 관측

첫 전체 실행은 70 passed, 1 failed였다. 실패는 템플릿 삭제의 DOM 확인이며,
첨부 기록에서 DELETE 시작 1731ms, 204 헤더 및 본문 완료 6683ms로 **4952ms**가
걸렸다. 다른 같은 테스트의 요청들은 약 100~150ms였다. 이 요청은 5초 assertion
경계에서 성공 응답이 도착한 사례로, 서버 오류 상태나 최초 목록 경합은 관측되지 않았다.
템플릿은 응답 뒤 캐시를 직접 갱신하므로 생성·삭제 응답만 기다린 뒤 DOM을 검증하도록
보완했다. 태스크처럼 존재하지 않는 후속 GET을 요구하지 않는다.

최종 검증: `git diff --check`, `pnpm lint` 통과. 위 실패를 보완한 뒤 영향받는
`task`, `weekly-monthly`, `navigation`, `template` 네 스펙을 재실행해 **20 passed
(38.5초, 재시도 없음)**를 확인했다. 앞선 전체 실행에서 나머지 스펙은 통과했으며,
최종 변경은 이 네 스펙과 해당 helper에 한정되어 전체를 중복 실행하지 않았다.
앱 코드·빌드 설정은 변경하지 않아 build와 워크트리 unit 검사는 선택하지 않았다.
로컬 통과가 당시 CI의 원격 지연 원인을 확정하거나 앱 경합을 해결했다는 뜻은 아니다.
