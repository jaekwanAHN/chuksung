# 접근성 기준

이 문서는 #102 에서 확인한 공통 레이아웃의 접근성 결함과, 앞으로 새 UI 를 쓸 때
지킬 기준을 남긴다. 코드에는 이 문서로 가는 포인터만 둔다.

Lighthouse 접근성 점수는 **자동 audit 만** 반영한다. 100 이어도 키보드 이동·포커스
순서·스크린리더 흐름은 별도 확인 영역이다 (`docs/perf/README.md`).

## 색 대비 — 기본값은 `zinc-600`

앱은 **라이트 전용**이다 (`globals.css` 의 `color-scheme: light`, `src/` 에 `dark:`
유틸리티 0건). 헤더 드롭다운은 다크 전환이 아니라 primary 테마 4종 선택이고,
테마는 accent 만 바꾸는 게 아니라 **`--color-zinc-*` 스케일 자체를 덮어쓴다**
(`src/lib/themes.ts`). 따라서 대비는 테마 4종 × 배경으로 각각 성립해야 한다.

oklch → sRGB 로 환산해 계산한 대비비:

| 테마 | 배경 | `zinc-300` | `zinc-400` | `zinc-500` | `zinc-600` |
|---|---|---:|---:|---:|---:|
| base | `#fafafa` | 1.42 | 2.52 | 4.63 | 7.41 |
| emerald | `#f0faf4` | 1.43 | 2.53 | **4.60** | 7.37 |
| indigo | `#f0f2fa` | 1.40 | 2.49 | 4.64 | 7.43 |
| red | `#faf0f0` | 1.40 | 2.51 | 4.67 | 7.48 |
| (흰 카드 위) | `#ffffff` | 1.48~1.57 | 2.63~2.80 | 4.83~5.23 | 7.73~8.37 |

WCAG AA 요구치는 일반 텍스트 4.5:1 이다. 여기서 나오는 규칙:

- **`zinc-400` 이하를 텍스트에 쓰지 않는다.** 어떤 테마에서도 2.5:1 대에 머문다
- **`zinc-500` 을 새로 쓰지 않는다.** emerald 에서 4.60 으로 요구치와의 여유가
  0.1 밖에 없어, 테마 값이 조금만 움직여도 조용히 기준을 넘긴다
- **보조 텍스트의 기본값은 `zinc-600`** 이다. 최악 테마에서도 7.37:1 로 여유가 있다
- 예외는 `MonthMiniCalendar` 의 비당월 날짜 하나다. 당월(`zinc-800` + `bg-zinc-50`)
  과의 위계를 남겨야 하고, 흰 카드 위라 `zinc-500` 이 4.83:1 로 여유가 생긴다

### 색만으로 위계를 만들지 않는다

모바일 하단 탭은 활성/비활성을 색 하나로 구분하고 있었다. 비활성을 `zinc-600` 으로
올리면 대비는 통과하지만 그 구분이 약해진다. 활성 쪽에 `font-semibold` 를 더해
**색이 아닌 축**을 하나 추가했다. 대비를 고치면서 구분이 사라지는 교환을 하지 않는다.

## 접근 이름 — 반응형으로 숨긴 라벨은 이름이 아니다

헤더 테마 트리거의 라벨은 `<span className="hidden sm:inline">` 이었다. `sm` 미만에서
DOM 에는 남지만 숨겨지므로, 버튼에 남는 것은 색 점 `<span>` 과 아이콘뿐이고 **접근
이름이 빈 문자열이 된다.** 데스크톱 폭에서만 통과하던 이유다.

`aria-label` 에 **보이는 라벨 텍스트를 그대로 포함**시켜 WCAG 2.5.3(Label in Name)
까지 함께 만족시킨다 — 음성 입력 사용자가 화면에 보이는 말로 버튼을 부를 수 있다.

`aria-haspopup="menu"` 는 **일부러 붙이지 않았다.** 현재 팝오버는 Tab 으로 순회하는
버튼 묶음이다. `menu` 역할을 선언하면 화살표키 로빙 포커스까지 구현해야 하고,
선언과 실제 동작이 어긋나면 스크린리더 사용자에게 오히려 손해다. 상태만 `aria-expanded`
로 알린다.

## heading 단계를 건너뛰지 않는다

`/daily` 는 `h1`(날짜) 다음이 곧바로 `TaskCard` 의 `h3` 라 `h2` 단계가 비어 있었다.

`TaskCard` 의 `h3` 를 `h2` 로 올리면 audit 은 통과하지만 **태스크 하나하나가 페이지
최상위 섹션**이 되어 구조가 뒤틀린다. 대신 `TaskList` 가 `heading` prop 을 받아
`<h2 className="sr-only">` 를 렌더한다. 화면은 그대로고, 스크린리더에는 건너뛸 수
있는 섹션이 하나 생긴다.

## 어떻게 확인했나

`pnpm perf` 의 A11y 점수는 **쓰지 못했다.** 하네스가 대시보드 대신 로그인 화면을
재고 있다 (#145 — `extraHeaders` 로 쿠키를 고정해 토큰이 회전하면 401 → `/login`).

대신 같은 Lighthouse 를 쓰되 쿠키를 **브라우저 쿠키 저장소**에 심어
(`launchPersistentContext` + `addCookies`) 접근성 카테고리만 수정 전후로 측정했다.
매 run 마다 `lhr.finalDisplayedUrl` 이 요청 경로와 같은지 검사했다 — #145 가 넉 달
가까이 조용했던 이유가 이 검사의 부재다.

| Page | A11y 전 | A11y 후 | 수정 전 실패 audit |
|---|---:|---:|---|
| /daily | 89 | **100** | `button-name`(1) · `color-contrast`(11) · `heading-order`(1) |
| /monthly | 90 | **100** | `button-name`(1) · `color-contrast`(13) |
| /weekly | 90 | **100** | `button-name`(1) · `color-contrast`(11) |

수정 후 세 페이지 모두 실패 audit 0건이다. 기준선 수치는 이슈 #102 가 기록한 값
(89/90/90)과 정확히 일치했다 — 하네스만 고장나 있었을 뿐 결함 자체는 그대로였다는
뜻이다.

## 남은 것

이번에 고친 것은 공통 레이아웃과 `/daily` 다. `zinc-400` 텍스트는 아직 다른
화면에 남아 있고(`/history`·`/jobs`·`/timer`·`/goal`·`DdayManager`), `TaskCard` 의
완료된 태스크 제목(`text-zinc-400 line-through`)도 같은 결함이다. 후자는 완료
태스크가 있는 계정에서만 audit 에 잡혀 이번 측정에는 나타나지 않았다 — **점수가
100 이라고 해서 그 화면에 결함이 없다는 뜻은 아니다.**

**이 측정은 일회성이고 `docs/perf/history.md` 원장에 쓰지 않는다.** 원장의 단일
경로는 `pnpm perf` 이고, 그것이 다시 신뢰할 수 있게 되는 시점은 #145 가 고쳐질
때다. 이 결함군의 상시 방어선을 세울 자리도 거기다.
